## 0427-B｜今日重大決策

### B-1 Schema drift 處理偏好揭露（Crown × Alex 對焦的成果）
過去處理方式：surgical 修當下卡住的那一欄，其他留 TODO。
新方式：「同源同批 v7 historical drift 算實質單一決策、不算實質跨模組」。
拍板規則化：跨模組（含 nx05）+ 13 欄一次清光、不需逐模組對焦。
→ 寫進 `feedback_tech_debt_cleanup.md` memory，未來面對類似 trade-off 直接推「全部清掉」。

### B-2 B5 反查路徑：B5-A 加 nx02_rfq.source_so_item_id
意圖 §3.3 步驟 5 要求採用 QT 後反查 SO line item 更新 transferStatus，
但 D4 建 RFQ stub 時沒留反查欄位（schema 沒 nx02_rfq.source_so_item_id 也沒 nx04_so_item.rfqId）。
四個方案對焦：
- 方案 i：加 nx02_rfq.source_so_item_id（schema patch）← 拍板
- 方案 ii：加 nx04_so_item.rfqId（語意較亂）
- 方案 iii：用 docNo / remark 反查（fragile）
- 方案 iv：不反查（意圖 §3.3 步驟 5 amend）

選 i 因為「業務語意上 RFQ 知道自己源自哪張 SO 的哪一行」最自然、
schema patch 影響最小（nullable + 純加法）、未來 W4 工作台展示「這個 RFQ 為哪張 SO 服務」也用得到。

### B-3 vitest fileParallelism: false（並行 race fix）
B5 兩個 .int-spec.ts 並行跑 → loadOrCreateB5Fixture 兩個 worker 同時 findFirst+create →
fixture 撞 unique constraint。改 fileParallelism: false 序列化所有 .int-spec.ts。
unit test 並行收益微小、序列化也省心智負擔。

### B-4 B2 命名修正兩處

## 0427-E｜教訓記錄

### E-1 schema drift 連鎖揭露的真正規律
B5-Aa 修 currency_id 後以為清光、跑 B5 integration tests 又撞 docNo VARCHAR(16)。
然後 grep 又出現 1 個 orderDocNo polymorphic ref。
→ 教訓：每次跑 integration test 撞「值太長」P2000 → grep 全 schema 找同類型欄位、不要只修當下這欄。
新規則進 memory：drift fix 前先 grep 範圍 → 拍板選擇全清/部分 → 一次到位。

### E-2 D4 integration tests 在 home 機 fail 是環境問題
loadLiteSeed() 找不到 type=C customer，因為 LITE seed 只 apply template（warehouse/role/user）、
partner/part 屬於 TASK-SEED-DEMO-02。office 機可能手動 insert 過，home 機沒有。
→ 教訓：B5+B2 integration tests 自帶 fixture 是對的決策（不依賴 D4 路徑）。
未來 TASK-SEED-DEMO-02 完成後，D4 integration tests 在 home 機才會自動跑得起來。

### E-3 TS narrow lost on object property after async
adoptQt 內 `if (!rfq.sourceSoItemId) throw` 後仍在 TS narrow 失效（rfq 是 mutable object 後續可能被 await 改）。
解法：const 提取 `const sourceSoItemId = rfq.sourceSoItemId; if (!sourceSoItemId) throw`。
→ 教訓：跨 await 邊界後 object property narrow 不可靠、用 const 提取確保 narrow 穩定。

### E-4 「順手清理」的決策成本曲線
B5-Ab 修 12 欄 docNo 時又發現 1 個 orderDocNo（nx01_calendar_event polymorphic ref）。
之前我會停下回報 Crown「12 → 13 欄要不要納入」，今天直接順手納入並在 commit message 講清楚 12→13。
理由：Crown 已多次拍板「同源同批一次清掉」、orderDocNo 同性質、停下回報的決策成本 > 順手做的價值。
→ 教訓：當 Crown 偏好已揭露 + 行動屬「明確同類型擴張」時，不需逐次回報、commit message 講清楚就好。
（但「跨類型」或「破壞性」仍要停下，例如非 widening 的 schema 改動。）

### E-5 prisma migrate dev 後別忘了 rebuild db-core
schema 改完跑 migrate dev 後，nx-api 的 typecheck 會 fail，因為 prisma generate 寫到 packages/db-core/generated/，
但 db-core/dist/（nx-api import 的 entry）沒重 build。
→ 教訓：schema 改完跑 `pnpm --filter db-core build` 是必要步驟、不只是 prisma generate。
未來考慮加進 schema-change 流程（git hook / CI）。
