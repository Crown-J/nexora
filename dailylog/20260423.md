## 0423-C｜關鍵技術決策

### 1. DOCK 全移除（Phase 2.5 推翻 v1 設計）

**背景**：R7 v1 spec 規畫手機版「雙層底部 bar」=「全站 DOCK（跨中心）+ 4 分區 Tab（中心內）」。Phase 2 實作後 Crown 立即推翻。

**Crown 的設計哲學修正**：
```
中心 ≠ 功能模組
中心 = 角色工作台

業務的中心 = 銷售中心（包含查庫存等所有業務需要的功能）
倉管的中心 = 庫存中心（倉管不接觸客戶）
業務根本不該進庫存中心（那是倉管的世界）

→ 底部 DOCK（中心切換）對業務是雜訊
→ 跨中心切換 = 「換身份」級動作 → 由 TopBar 星球承擔
```

**實作**：`MobileDock` 函式頂層 `if (!isDashboardHome) return null`，首頁 quickShortcuts 保留，其他中心不 render DOCK。元件檔案、舊 JSX、`HIDE_MOBILE_DOCK_*` 常數全保留為死碼，未來要恢復 `git revert 10841d3` 即可。

**延伸結果**：`MobileHubSectionTabs` 原本的 `offsetBottom` prop 在 Phase 2 加過，Phase 2.5 後銷售中心不再使用（SectionTabs 直接貼底），但 prop 保留向後相容（未來跨中心需要堆疊時可復用）。

### 2. Zustand 作為前端狀態管理

**背景**：R7 Phase 7 的 RFQ/QT/CO 需要跨元件、跨路由共享狀態（Step2 建 RFQ / 同行調貨列表 / 詳情頁 / 狀態追蹤 / QT 詳情頁都要讀同一份）。useReducer 只能單頁。

**決策**：引入 `zustand@^5.0.12`（`apps/nx-ui/package.json`）。選它不選 Redux 理由：
- 最小 API 面積（`create` + hook）
- 無 provider 包裹
- 多個 hook call 可自動 memoize selector

**首個 store**：[`features/sale/ui/inquiry/store.ts`](../apps/nx-ui/src/features/sale/ui/inquiry/store.ts) 管 RFQ / QT / CustomerOrder
- 單據編號 `generateDocNumber` 自動遞增流水（從現有單找最大）
- `adoptVendorQuote` 和 `createDirectQTs` 是 QT 生成的兩條路徑（同行調貨採用 vs 業務直接報價）

**架構債登記 A007**：未來 Phase 5~7 的 SO / PK / BX / DN / IT 也會需要 store。評估是否把 inquiry store 擴成 `sale/ui/sales-store.ts` 整合，還是開新 store 各管。建議開新 `sales-store.ts` 包 SO/PK/BX/DN，`inquiry store` 繼續管 RFQ/QT（上游），跨中心連動透過 action 呼叫彼此。

### 3. 跨中心架構範本（spec 已定，大塊 2~4 實作）

## 0423-D｜關鍵業務決策（Crown 親口）

### 1. 庫存哲學 — 物理定律

> 「我不希望我的系統庫存出現負數。」

延伸：ERP 系統必須反映物理世界。任何讓庫存變負的設計 = 系統脫離現實。OOS 分流（R7 Phase 7）、SO 備貨 4 情境（業務重構 Phase 5）、RFQ→QT→TI→SO 單據鏈都是這條哲學的實體化。

### 2. 單據鏈 RFQ→QT→TI→SO

Alex 原本設計「詢價採用 → 直接建 SO」被 Crown 修正：
```
階段 1：RFQ 詢價單（同行還沒回覆）
階段 2：QT 報價單（同行回覆後，業務決定售價給客戶）
階段 3：TI 調貨單（客戶確認 QT 後才調貨，此時貨才進本倉）
階段 4：SO 銷貨單（庫存到位才扣貨出給客戶，全程 >= 0）
```

**R7 Phase 7 範圍**：僅做階段 1 + 階段 2（RFQ / QT）。TI / SO 等待大塊 2。

### 3. STEP 5 客戶回應 5 選項（非 3 選項）

> 「客戶可能部分接受、考慮看看、全部不要，原 3 選項涵蓋不全。」

新 5 選項（業務重構 Phase 3 已實作）：
- `accept_all` 全接受並下單
- `partial_accept` 部分接受（勾選要的品項）
- `price_adjust` 要求調整價格（逐項改單價 + 即時毛利試算）
- `consider` 考慮看看（記錄 QT pending_customer + 追蹤天數）
- `reject` 全部不要（選流失原因 + 備註）

### 4. 追蹤清單只放「需採取行動的單」

> 「追蹤清單只需要追蹤未完成的銷貨單及調貨單，詢價和報價就不追蹤了，但是詢價跟報價一樣，若是一個月內有相同對象相同品項都要跳出提醒。」

**實作**（業務重構 Phase 4）：
- StatusSection 移除「詢價待回覆」「待確認報價」兩個群組（R7 Phase 7 才剛加就移除）
- 改為「銷售進行中 / 調貨進行中 / 保固待結果」3 群組
- 詢/報的提醒改由 `useHistoryRecord` hook 在 S03 查料時主動推播

### 5. 碎片化詢問（追加品項機制）

> 「A1001 跟我詢問 X 零件報價，我報了之後，他說 OK，所以我就按下客戶接受並下單，這時他又說那 Y 零件呢？」

**實作**（業務重構 Phase 3）：Step2 加入清單後彈 `AddMoreDialog` 問「還要查 / 沒了」，業務可不斷回頭查下一個料號直到客戶說「就這些」。

### 6. 毛利警覺性（Crown 強調）

> 「要顯示建議報價及毛利，讓業務有警覺性。」

`MarginAlert` 即時計算並染色：達標綠 / 略低金（target-5）/ 過低紅。業務改價時即時更新，避免無意識砍價。
