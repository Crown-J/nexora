### 8. 🔥 React #185 教訓 — Zustand selector pattern（Production hotfix）

**現象**：Crown 手機登入 `/dashboard/sale` 白屏 + console `Uncaught Error: Minified React error #185`。

**Root cause**：Phase 7 / Phase 8 兩個 StatusSection 的 selector 寫法錯誤：
```tsx
// 壞（每次都回新 array reference，Zustand Object.is 判為「變」→ 無限 loop）
const activeSOs = useSalesStore((s) =>
  s.sos.filter((so) => ACTIVE_SO_STATUSES.includes(so.status))
);
```
Dev mode React 19 容忍（只印警告），production build 直接拋 #185（Maximum update depth exceeded）。

**修法**（hotfix commit `6f3c45b`）：
```tsx
// 好（selector 只取 slice，reference 穩定；filter 搬進 useMemo）
const allSos = useSalesStore((s) => s.sos);
const activeSOs = useMemo(
  () => allSos.filter((so) => ACTIVE_SO_STATUSES.includes(so.status)),
  [allSos],
);
```

**後續規範**（架構債 A014）：任何 `useSalesStore` 或 `useRFQStore` 的 selector **只取原 reference slice**（`s.xxx`），不在 selector 內做 `.filter()` / `.map()` / `.sort()` 等產生新 reference 的操作。Derive 一律用 `useMemo` 或 Zustand 的 `shallow` equality。

## 0423-D｜關鍵業務決策（Crown 親口）

### 1. 庫存哲學 — 物理定律

> 「我不希望我的系統庫存出現負數。」

延伸：ERP 系統必須反映物理世界。任何讓庫存變負的設計 = 系統脫離現實。OOS 分流（R7 Phase 7）、SO 備貨 4 情境（業務重構 Phase 5）、RFQ→QT→TI→SO 單據鏈都是這條哲學的實體化。

### 2. 單據鏈 RFQ→QT→TI→SO

Alex 原本設計「詢價採用 → 直接建 SO」被 Crown 修正：
```
階段 1：RFQ 詢價單（同行還沒回覆）
階段 2：QT 報價單（同行回覆後，業務決定售價給客戶）
階段 3：TI 調貨單（客戶確認 QT 後才調貨，此時貨才進本倉）
階段 4：SO 銷貨單（庫存到位才扣貨出給客戶，全程 >= 0）
```

**R7 Phase 7 範圍**：僅做階段 1 + 階段 2（RFQ / QT）。
**大塊 2 Phase 5~7 範圍**：補齊階段 3 + 階段 4（TI + SO + PK/BX/DN 連動），Crown 庫存哲學完整落地。

### 3. STEP 5 客戶回應 5 選項（非 3 選項）

> 「客戶可能部分接受、考慮看看、全部不要，原 3 選項涵蓋不全。」

新 5 選項（業務重構 Phase 3 已實作）：
- `accept_all` 全接受並下單
- `partial_accept` 部分接受（勾選要的品項）
- `price_adjust` 要求調整價格（逐項改單價 + 即時毛利試算）
- `consider` 考慮看看（記錄 QT pending_customer + 追蹤天數）
- `reject` 全部不要（選流失原因 + 備註）

### 4. 追蹤清單只放「需採取行動的單」

> 「追蹤清單只需要追蹤未完成的銷貨單及調貨單，詢價和報價就不追蹤了，但是詢價跟報價一樣，若是一個月內有相同對象相同品項都要跳出提醒。」

**實作**（業務重構 Phase 4 + Phase 7）：
- StatusSection 移除「詢價待回覆」「待確認報價」兩個群組（R7 Phase 7 才剛加就移除）
- 改為「銷售進行中 / 調貨進行中 / 保固待結果」3 群組
- 詢/報的提醒改由 `useHistoryRecord` hook 在 S03 查料時主動推播
- Phase 7：這 3 群組改從 `useSalesStore` 動態衍生（不再 mock）

### 5. 碎片化詢問（追加品項機制）

> 「A1001 跟我詢問 X 零件報價，我報了之後，他說 OK，所以我就按下客戶接受並下單，這時他又說那 Y 零件呢？」

**實作**（業務重構 Phase 3）：Step2 加入清單後彈 `AddMoreDialog` 問「還要查 / 沒了」，業務可不斷回頭查下一個料號直到客戶說「就這些」。

### 6. 毛利警覺性（Crown 強調）

> 「要顯示建議報價及毛利，讓業務有警覺性。」

`MarginAlert` 即時計算並染色：達標綠 / 略低金（target-5）/ 過低紅。業務改價時即時更新，避免無意識砍價。

### 7. 倉管中心第 4 分區 = 倉位管理（非客戶維護）

> 「倉管不接觸客戶。」

**實作**（業務重構 Phase 8 + Phase 10）：
- 銷售中心 4 分區：狀態追蹤 / 工作站 / 單據管理 / **客戶維護**

- 倉位管理含「建議安全量 vs 採購設定」比對，倉管看坪效給採購建議

### Bug 本質

```tsx
// ❌ Bug 版本（sale StatusSection + inventory StatusSection）
const activeSOs = useSalesStore((s) =>
  s.sos.filter((so) => ACTIVE_SO_STATUSES.includes(so.status))
);
```

每次 React render → selector 跑一次 → `.filter()` 產生新 array reference → Zustand 用 `Object.is` 比較前後 snapshot → 判定「變了」→ 觸發 re-render → selector 再跑 → 新 reference → 無限迴圈 → React 保護機制拋 #185。

### 為什麼 dev mode 沒重現

React 19 在 dev mode 對 `useSyncExternalStore` 的 getSnapshot stability 有額外保護（印警告後 cache 舊 snapshot 避免 loop）。Production build 移除這層保護，直接讓 loop 觸發。

### 修正

```tsx
// ✅ 正確版本
const allSos = useSalesStore((s) => s.sos);  // 原 array reference 穩定
const activeSOs = useMemo(
  () => allSos.filter((so) => ACTIVE_SO_STATUSES.includes(so.status)),
  [allSos],
);
```

### 範圍盤點（已全檢）

Grep `useSalesStore\(\(s\) =>` 全部 10 處：
- 9 處只取原 reference（`s.sos` / `s.its` / `s.pks` / action functions）— ✓
- 1 處 Step8 的 `.find()` 回單一 object 或 null（primitive 穩定）— ✓
- 2 處 StatusSection 的 `.filter()` — 🔥 本次修復
- DocumentsSection 的 filter 是在 component body 內做 `.length`（回 number），不在 selector 內 — ✓
