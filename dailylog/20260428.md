## 0428-B｜今日重大決策

### B-1 Schema drift 兩波清光（同 v7 historical drift 邏輯延續）

連續兩個欄位（part_brand.code VARCHAR(3) + brand_code_rule.name VARCHAR(15)）撞 P2000 LengthMismatch。
跟 Phase 0 16 欄一次清光不同 — 這次每波 audit 後**只 1 欄需修**：
- 第一波：part_brand.code（撞 catalog 13 sub-brand 撞 HND 縮寫）→ widen 10
- 第二波：brand_code_rule.name（撞 'Mercedes-Benz 編碼規則' 18 字）→ widen 50

兩次拍板相同邏輯：「業界真實感是 NEXORA 賣點 + isolated 緊縮設計修正」。
audit 範圍：全 schema 60 個 name 欄位、僅這兩個 name 緊縮。

### B-2 DEMO-02 staging 拆三波（Crown 拍板）

過去 seed 全跑、要嘛全綠要嘛全炸。這次拍板：
- LITE 先跑 → Crown + Alex review 真實感 → 過了才進 PLUS
- PLUS 跑 → review → 過了才進 PRO
- 任一波發現問題（業務情境覆蓋 / 真實感）→ 該波修正 + 重跑、不影響後續波

理由：
- demo data 量大（LITE ~263 / PLUS ~1100 / PRO ~3500 row）一次跑壞修正成本高
- 真實感問題只能跑出來才看得到、不是寫 code 階段能 catch
- 三波拆分讓 review feedback 可早期收斂模板

### B-3 客戶名真實感 = NEXORA pitch 賣點

LITE 第一版客戶名「信義誠信汽車材料行」6-7 字工整、像連鎖企業。
Crown 業界範例：「全興汽材 / 三和零件 / 老吳輪胎」4-5 字個體戶老店感。
拍板：fix LITE + 改 catalog 模板（不只 SQL UPDATE 8 筆、要根本上改模板讓 PLUS/PRO 也產出真實感）。

業種池：汽材 / 零件 / 汽修 / 輪胎（口語短，不再「汽車材料行 / 汽修廠」）。

## 0428-E｜教訓記錄

### E-1 Schema drift 連環撞、audit 比 surgical 修更省往返
0427 兩波 currency_id + docNo widening 後以為 schema drift 清光、今天又連環撞兩個 name 欄位。
規律：每次跑 LITE seed 撞 P2000 → audit 同類型 → 拍範圍 → 一次清完。
新規則進 memory：跑 demo seed 撞「值太長」P2000 → 立刻 audit 同類型欄位（不只修這欄）。

### E-2 業界真實感比 mock data 邏輯難寫
Hank 寫 idempotent seed 邏輯、stock_balance 金字塔分布、5 種接龍鎖狀態都順利。
但客戶名第一版「信義誠信汽車材料行」業界看了不對勁。
教訓：mock data 真實感需要「業界 muscle memory」（Crown 的 NEXORA 賣點），
不是「邏輯正確 + 隨機分布」就夠。
新規則進 memory：mock data 第一版必先給 Crown preview 業界感、再進 SQL/seed 落地。

### E-3 catalog 模板 vs SQL UPDATE：根本修
Crown 對「LITE 8 個客戶名歪」拍板「改模板（不只 SQL UPDATE 8 筆）」。
理由：PLUS 40 / PRO 120 客戶會用同模板、現在不修模板等於把問題推到 168 筆才發現。
教訓：seed code 是 source of truth、SQL UPDATE 只是 quick fix；catalog/builder 級的問題要從根本改。

### E-4 staging 拆三波省回滾成本
LITE 跑壞兩次（兩次都 schema drift），但因為只跑 LITE（~263 row）每次撞修很快。
若一次跑 LITE+PLUS+PRO 全部、撞 schema drift 要 truncate ~10000 row 重跑。
教訓：demo seed 規模超 1000 row 一定要分波、跟 schema migration 多階段同精神。
