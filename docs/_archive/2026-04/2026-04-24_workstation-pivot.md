# Workstation Pivot — 從「流程式 SOP」轉向「動作式工作台」

> 決策日期：2026-04-24
> 決策者：Crown Lin
> 紀錄者：Alex（Claude PM AI）
> 對應 Code 基準：commit `3e95fb8`（`feature/spec-reverse-sw01` 分支起點）
> 文件類型：ADR（Architecture Decision Record）

---

## 一頁摘要

**今天發生了什麼**：

從早上 TASK-SPEC-REVERSE-S-W01 反推 spec 的 11 ⚠️ 出發，演變為 NEXORA 前端在 R7 之後最大的一次設計轉向：

> **「銷貨中心 → 國內銷售」從一條 SOP 9 step 流程，拆成 5 個獨立工作台。**

**核心理由**：

業務真實工作不是 linear，是 dispatch-style。SOP 9 step 是「順暢時的劇本」，無法處理「客戶臨時加減料、改取貨方式、本來要調貨改下訂單」這類業界 70% 以上的真實變數。Crown 18 年業界經驗 + 偉盟系統的 7 張參考截圖共同證實：業界做法是 keystroke-driven 的工作台，不是 wizard-driven 的流程。

**5 個核心決策**：

| # | 主題 | 決策 |
|---|------|------|
| Q1 | 即時查詢 vs 即時報價 | **合併**為「即時查詢報價」單一工作台，4 個快捷鍵子區 |
| Q5 | 沒庫存能否建 SO（超賣） | **方案 C**：軟鎖 + 強制標來源（受控的超賣） |
| Q6 | SO 與 BX/DN 關聯 | **1 SO : 1 PK : N BX : N DN**（依包裝體積拆批） |
| Q7 | 明細修改規則 | 分階段：建立中/待撿貨自由改、撿貨中警告、撿貨完後加項生新 PK、配送中後禁止 |
| Q8 | R7 SOP code 怎麼處理 | **保留**在 `/sop-demo` 路徑，定位為「教學/新人模式」 |

**對 PROJECT_CONTEXT 哲學的影響**：第 2 條（庫存定律）、第 3 條（工作站=SOP）、第 7 條（SYS-C 自動判斷）三條哲學要修正，不是廢除。

**這份文件的角色**：所有後續重設計 task（5 個新工作台 spec、SO data model 改寫、SYS-C 重寫）的根據。實作時若與本文件衝突，以本文件為準。

## 二、設計轉向（Pivot）

### 2.1 從「流程式 UI」轉向「動作式 UI」

| 維度 | 原（R7 Phase 7 + 大塊 1~3） | 新（本次決策） |
|---|---|---|
| 心智模型 | wizard-driven（精靈引導） | dispatch-driven（業務排派） |
| 入口結構 | 一條 SOP 9 step | 5 個原子工作台 |
| 適用情境 | 順暢、線性、教學 | 變數多、跳接、實戰 |
| 業務狀態連續性 | reducer 內部一路帶 | 工作台間可選擇傳遞 |
| 學習曲線 | 新人友善、老手嫌慢 | 老手快速、新人需引導 |

### 2.2 5 個新工作台

```
銷貨中心 → 工作站 →
  1. 即時查詢報價作業（合併查詢與報價）
  2. 國內銷貨作業
  3. 銷售退回作業
  4. 同行詢價作業
  5. 同行調貨作業
```

新增第 6 個入口（不在「工作站」分區，而是「教學/示範」獨立入口）：
```
  6. 銷貨 SOP 教學模式（保留 R7 既有 code 於 /sop-demo）
```

### 2.3 對 PROJECT_CONTEXT 哲學的影響

| 哲學條目 | 原內容 | 變化 | 修正方向 |
|---|---|---|---|
| 第 1 條 | 中心 = 角色工作台 | **強化** | 工作台原則往下一層延伸——工作站本身也是工作台、不是流程 |
| 第 2 條 | 庫存 >= 0 是物理定律 | **修正** | 區分「物理庫存 >= 0」（守住）與「會計承諾可超出」（放開） |

## 三、偉盟參考（業界事實）

Crown 提供 7 張偉盟系統真實截圖作為設計參考。以下是從中提煉的事實：

### 3.1 keystroke 鏈

偉盟「料號即時查詢」是入口，3 個快捷鍵展開不同子視窗：

```
F2  → 即時查詢主畫面（庫存數量、價格、車型、備註）
Alt+7 → 庫位資料查詢（每個倉的庫位分布）
Alt+2 → 銷貨比價查詢（這個料號賣給所有客戶的歷史）
   └─ Alt+F → 篩特定客戶
   └─ F8   → 立即報價（彈窗，帶入客戶 + 單價 + 車型）
```

從查料到出報價是一條 keystroke 鏈，**不是兩個獨立功能**。

### 3.2 5 個業界事實

1. **查詢與報價是同一動作的不同切面**——把它們設計成兩個工作台會違反業務直覺
2. **歷史資料是主役不是輔助**——偉盟「銷貨比價」面板佔半個畫面、24 筆歷史一次列出。NEXORA 原設計的「Step 2 角落小提示」份量太輕
3. **報價/銷貨/訂單共用一張表，用 checkbox 切**——單號中字母（A=報價、Z=銷貨、O=訂單）是類型代碼。一個畫面看歷史、一個畫面建新單
4. **銷貨單允許超賣，業務在備註欄手標來源**——這條最關鍵（見第四章 Q5）
5. **庫位分倉、可出貨量會變負**——偉盟的 Z01 台北倉「可出貨量 -18」是正常狀態，不是 bug

### 3.3 Crown 對偉盟的批評

Crown 在拍板方案 C 前說的關鍵一句：

> 偉盟目前就是因為沒有鎖，導致公司現在要追庫存會一團亂，**不知道這負數是哪裡來的**，尤其倉庫很多之後，你要一個個的往回追。

偉盟的問題不是「允許超賣」，是「允許**失控的**超賣」：備註欄是 free text、不強制、無補貨綁定、無責任分配。NEXORA 的方案 C 解決的正是這個。

## 四、5 個核心決策

### 4.1 Q1 — 即時查詢報價工作台合併

**決策**：合併「即時查詢」與「即時報價」為單一工作台「即時查詢報價」。

**4 個快捷鍵子區**：
```
查庫存（預設）→ 看庫位 → 看歷史 → 立即報價
```

**理由**：
- 偉盟事實 1 + 事實 2：業界本來就是同一條 keystroke 鏈
- 業務 80% 開查詢就是要報價，分兩個工作台會讓業務搞混入口
- 20% 純查詢的情境，自然停在第一個子區「查庫存」即可
- 子區之間用快捷鍵切換、共享頂部的「料號 + 客戶」上下文

**替代方案為何不選**：
- 兩個工作台平行 → 違反偉盟驗證過 18 年的業界 muscle memory
- 隔裡隔塔（先合併、用了取再分） → 後拆比先合難太多

**影響範圍**：
- 新工作台檔案結構：`features/sale/ui/instant-quote/`
- URL：`/dashboard/sale/instant-quote`
- 4 子區用 query state（`?tab=stock|location|history|quote`）
- 與 SOP 的 Step 2「查料」共享 `MOCK_PARTS_DB` / `MOCK_HISTORY_PRICES`，重用度高

### 4.2 Q5 — 軟鎖 + 強制標來源（方案 C）

**決策**：採方案 C「軟鎖 + 強制標來源」。

#### 4.2.1 三方案對照

| 維度 | 方案 A 硬鎖 | 方案 B 偉盟全開 | **方案 C（採用）** |
|---|---|---|---|
| 沒庫存能建 SO 嗎 | ❌ 不能 | ✅ 可以、空白也行 | ✅ 可以、但必須標來源 |
| 業務動線 | 慢（先解決缺貨才建單） | 快（隨便建） | 快（一個下拉一鍵搞定） |
| 備註結構 | N/A | free text | 結構化下拉選單 |
| 補貨責任 | 系統強制（無法逃避） | 業務自己記得 | 系統強制（必填）+ 自動建單 |
| 物理庫存 >= 0 | ✅ 守住 | ⚠️ 邏輯模糊 | ✅ 守住（物理 vs 會計分離） |
| 追庫存能力 | N/A | ❌ 黑洞 | ✅ 完整審計鏈 |
| 偏離業界程度 | 高（被罵難用） | 低 | 低 |
| 新人友善 | 高（不會出包） | 低（要記住規矩） | 中（必填下拉有引導） |

#### 4.2.2 方案 C 的 4 條規則

```
規則 1：SO 允許「會計超賣」
  業務承諾數量可以 > 物理庫存
  目的：保住業務在電話上立即接單的速度

規則 2：超賣的 lineItem 必須結構化標來源
  本倉夠 → 備註欄不需要填（自動）
  本倉不夠 → 備註欄變必填，下拉選單：
    ○ 從 Z00 總倉調撥
    ○ 從 Z02 新莊調撥
    ○ 從 Z03 北投調撥
    ○ 同行調貨：[輸入同行代碼，如 D-O104]
    ○ 客戶訂單 CO（先記、不調）

規則 3：系統根據備註自動生單
  選「Z02 調撥」     → 自動建 IT-xxx，倉管調撥工作台立刻看到
  選「同行調貨 D-O104」→ 自動建 RFQ-xxx 或 TI-xxx（需設計細節）
  選「客戶訂單 CO」   → 自動建 CO-xxx，待補貨時提醒

規則 4：庫存帳分兩本
  warehouse_stock（物理庫存）：永遠 >= 0，反映倉庫真實盒子數量
  committed_stock（會計庫存）：可以為負，= 物理 - 已承諾未出
  業務看「可承諾數量」，倉管看「物理數量」，財務看「committed」
```

#### 4.2.3 哲學調整

PROJECT_CONTEXT 第 2 條原文：
> 「我不希望我的系統庫存出現負數。」這不是偏好，是物理定律。

修正為：
> **物理庫存 >= 0** 是物理定律（守住）。
> **業務承諾 > 物理庫存** 是允許的，但每筆超賣必須綁定結構化的補貨計畫（IT/TI/CO），系統自動生單追蹤。
> 這是「受控的超賣」——同時保住業務速度與庫存可追蹤性。

#### 4.2.4 為什麼這樣解決偉盟的痛

| 偉盟亂的根因 | 方案 C 解法 |
|---|---|
| 備註是自由文字、解析不出來 | 結構化下拉，欄位是 enum |
| 業務可以不標、忘了標 | 超賣時必填、不填無法存檔 |
| 標了「Z00」但沒人去調撥 | 系統存檔時自動建 IT，倉管立刻看到 |
| 不知道 -14 是誰造成 | 反查 committed_stock 來源 → 列出所有 SO 與 lineItem |
| 補貨單跟銷貨單沒關聯 | IT/TI 的 `relatedSoNumber + relatedLineItemId` 必填 |

### 4.3 Q6 — 1 SO : 1 PK : N BX : N DN 關聯改寫

**決策**：

```
1 張 SO（例：5 個料號）
  → 1 張 PK（撿貨單，一次撿完所有料號）
  → N 張 BX（包貨單，依包裝體積拆批，可能 1 張、可能 3 張）
  → N 張 DN（送貨單，通常跟 BX 對應，但拆批配送也可能再拆）
```

**理由**：

Crown 業界事實：「東西太大沒辦法包成一個就拆成多個 PACKAGE」。原 code 設計 1:1 是錯的，無法處理大件商品。

PK 維持 1:1 是合理的——撿貨是「把該拿的東西全部從庫位拿到打包區」一次動作；包裝才會因體積拆批。

**SO 顯示「備貨中」狀態的新邏輯**：

```
原 code：SO.status 直接被 BX/DN 的單一狀態驅動
新邏輯：SO.status 看「所有 lineItems 是否都進入待配送階段」
        UI 顯示「備貨中（5 項，3 項已包貨待配送、2 項待包貨）」
```

**影響範圍**：
- `fulfillment/types.ts`：BX/DN 加 `relatedSoNumber + relatedLineItemIds[]`
- `fulfillment/store.ts`：`completePicking` 不再「自動建 1 張 BX」，而是「進入包貨階段、待倉管決定包成幾張」
- `completePacking` 改為「完成這張 BX」而非「完成整個 SO 的包貨」
- 新增 `planSoFromLineItems(so)` helper：根據所有 lineItems 的 BX/DN 狀態算 SO 的整體狀態

### 4.4 Q7 — 明細修改規則

**決策**：分階段規則。

| SO 狀態 | 加減料號 | 行為 |
|---|---|---|
| 建立中 | ✅ | 自由改，無提示 |
| 待撿貨 | ✅ | 自由改，PK 自動重建 |
| 撿貨中 | ⚠️ | 警告「倉管正在撿貨，要中斷嗎？」業務可選擇繼續或取消 |
| 待包貨 / 包貨中 | ⚠️ | 加項：生新 PK 給新加項、原 PK/BX 不動；減項：警告「需重撿，確定嗎？」 |
| 待配送 | ❌ | 禁止改 |
| 配送中 / 已完成 | ❌ | 禁止改，要動就走銷售退回作業 |

**理由**：
- 配合方案 C 的「業務速度優先」精神，盡量讓業務能改
- 但不能讓業務瞎改打亂倉管動線——撿貨中改了會讓倉管手上的紙條變廢紙
- 撿貨完後加項，採「新加項生新 PK」模式而非「整張重撿」，避免重工
- 走銷售退回是底線——已經出庫的東西不能假裝沒事

**影響範圍**：
- 新工作台「國內銷貨」的明細編輯區要實作這個狀態機
- 新增 toast / dialog 元件（撿貨中警告、待包貨警告、加項生新 PK 提示）
- 倉管端要設計「PK 被中斷」的通知

---

### 4.5 Q8 — SOP 9 step 保留為教學模式

**決策**：R7 Phase 7 + 大塊 1~3 實作的 SOP 9 step 整套保留，路徑不變（`/dashboard/sale/sop-demo`），定位為「**教學模式 / 新人模式**」。

**理由**：
- 成本最低（不用刪 code、不用重寫）
- 保留新人引導價值（SOP 確實適合教學）
- 保留春酒已經跑過的 demo 路徑（之前的演練不浪費）

**警告**：

SOP 內的 SYS-C 是「自動判斷」邏輯，新工作台是「業務手標」邏輯，**這是不同 mental model**。新人從教學模式畢業到正式工作台會挫折。

兩條路徑可選（暫不決定）：
- 教學模式內的 SYS-C 也改成「強制標來源」的引導版（加 tooltip 說明）
- 教學模式維持 SYS-C，但 `/sop-demo` 入口加標題「這是 v1 簡化教學版，正式請用 [國內銷貨工作台]」

選哪個等做新工作台時再決定。

**影響範圍**：
- 不用改 code，現狀照舊
- 銷貨中心 hub 加新入口「📚 銷貨 SOP 教學模式」（與 5 個工作台分開呈現）
- 對應 11 ⚠️ 中與 SOP 相關的 bug（OrderPreview「生成中」、TodoGroup 不可點、mock 字串硬寫王大偉等）：屬於「教學模式內的 bug」，可選擇順手清或維持現狀

## 五、影響範圍（給未來 task 拆分用）

### 5.1 Data Model 改動

```
nx_part / nx_warehouse_stock：
  + warehouse_stock：物理庫存（永遠 >= 0）
  + committed_stock：會計庫存（= 物理 - 已承諾未出，可負）
  反查：committed_stock 來源 = 哪些 SO.lineItem 在等貨

nx_so_line_item（SO 明細）：

  + relatedCoId: string | null

nx_bx（包貨單）：

  + relatedLineItemIds: string[]（這張 BX 包了哪幾項）
  關聯改 1 SO : N BX

nx_dn（送貨單）：同 BX，1 SO : N DN
```
