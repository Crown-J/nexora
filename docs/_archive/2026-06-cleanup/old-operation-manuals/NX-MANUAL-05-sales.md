### 3.3 最低售價（minPrice）算法 ⭐

NEXORA 算「最低售價」用：

```
minPrice = 該料件在該倉的「庫存加權平均成本」 × (1 + 客戶等級 marginPct / 100)
```

舉例：

```
場景：和興汽車（B 級客戶、marginPct 15%）來買剎車片

剎車片庫存資訊：
  主倉的加權平均成本 = 100 元

minPrice 計算：
  minPrice = 100 × (1 + 15/100)
          = 100 × 1.15
          = 115 元

意思：給和興汽車賣剎車片、最低該 115 元、不到要寫理由。
```

如果換成 A 級客戶（marginPct 12%）：

```
  minPrice = 100 × 1.12 = 112 元（更低、因 A 級是大批發、毛利薄、給更便宜）
```

如果換成 D 級客戶（marginPct 22%）：

```
  minPrice = 100 × 1.22 = 122 元（更高、D 級是一次性、毛利厚）
```

### 3.4 ⚠️ 不算 minPrice 的 3 種情況

| 情況 | 系統行為 |
|---|---|
| 客戶沒綁 customerGradeId | minPrice 為 null、不啟動毛利保護 |
| 該料件該倉沒有 stock_balance 紀錄 | minPrice 為 null（料件還沒進過貨）|
| 庫存加權平均成本 = 0 | minPrice 為 null（成本還沒算出來）|

⭐ 對 LITE 客戶建議：**新建客戶時務必綁上 A/B/C/D 其中一級**、不綁就沒毛利保護、業務員可以隨便開價。

### 3.5 低於 minPrice 怎麼處理

⭐ **NEXORA 設計原則：不擋業務、只強制填理由（稽核用）**。

具體流程：

```
業務員填單價 < minPrice
   ↓
系統檢查：
   - 有沒有填「belowMinReason 為什麼讓利」？
     - 有 → 允許過、寫入 belowMinReason 稽核
     - 沒有 → 報錯擋住、提示「請填讓利理由」
   ↓
為什麼這樣設計：
   - 業務員有時要主動讓利搶單（例：客戶量大、新客戶試水溫、競爭對手低價）
   - 系統不擋業務、只留痕跡讓主管事後可查
```

範例 belowMinReason 填法：

```
場景：minPrice = 115、業務員想開 105

填法（必填）：
   「客戶這次量大（500 顆）、長期客、給予 8.5% 讓利搶單。
    後續若同條件再買、可比照處理。」
```

主管之後從報表「業務員讓利統計」可追蹤誰常讓利、是否合理。

### 3.7 跟料件主檔 A/B/C/D 售價的關係（已實際驗證）

NEXORA 料件主檔的「銷貨分區」有 priceA / priceB / priceC / priceD 4 個固定售價欄位（NX-MANUAL-02 §5.1）、跟「客戶分級毛利率」是**兩個不同的成本邏輯、聯手影響定價**：

#### 兩個獨立計算

| 名稱 | 是什麼 | 怎麼來 |
|---|---|---|
| **料件主檔 priceA/B/C/D** | 業務員 / 系統幫各級客戶事先訂的「**等級固定價**」| 手動填、或系統用「進貨成本 × (1 + 客戶分級 marginPct/100)」算建議值寫進來 |
| **建議售價**（系統算給業務員開單參考用）| 客訂預估價 / 開單時的「該開多少」| 系統算（見下 §3.7.A）|
| **minPrice**（最低售價守門）| 業務員真的開單時的最低底線 | 系統算（見下 §3.7.B）|

#### §3.7.A 系統算「建議售價」的公式

業務員開報價 / 銷貨單時、系統會用以下公式算出**建議單價**給業務員參考（業務員可手動改）：

```
建議售價 = max(
  90 天歷史採購成本加權平均 × (1 + 客戶等級 marginPct / 100),  ← 算法 1：成本加成
  該料件對應該客戶等級的 priceX                                ← 算法 2：等級固定價
)
```

兩個取**較高**那個當建議售價、為什麼？

- **算法 1 反映「最近真實成本」**：90 天內這料件從供應商買的均價、加上業務面預期的毛利。
- **算法 2 反映「業界既有定價」**：之前定好的標準售價、市場價的錨點。
- 兩個取較高 = **不讓系統建議的價低於這兩個錨點**、避免賤賣。

#### §3.7.B 系統算「minPrice 最低售價」的公式

業務員手動填單價時、系統算 minPrice 守門（前面 §3.3 已講）：

```
minPrice = 當前該倉的庫存加權平均成本 × (1 + 客戶等級 marginPct / 100)
```

#### §3.7.C 建議售價 vs minPrice 用的「成本」不同 ⚠️

⚠️ **重要釐清**（避免會計或業務員誤會）：

| 算法 | 用的成本 | 是什麼 | 何時用 |
|---|---|---|---|
| **建議售價** | **90 天歷史採購成本加權平均** | 跟供應商買進來的價、近 90 天的 | 系統幫業務員算「該開多少」|
| **minPrice 守門** | **當前該倉的庫存加權平均成本** | 帳上即時的庫存成本（含所有過去進貨累加）| 業務員填的單價要 ≥ 這 |

兩個數字**通常很接近、但會有差異**（庫存帳累積比 90 天歷史更久）。

#### §3.7.D 第 2 個系統預設值：無等級 20%（co-estimate 算法用）

⚠️ **重要、跟 §3.2 的 12/15/18/22 是不同 fallback**：

系統算「客訂建議售價」時、如果客戶**完全沒綁等級**：

- 不會用 A/B/C/D 中任一個的 marginPct（12/15/18/22）
- 而是用 hardcoded fallback **20%**（業界一般客戶毛利率）

| 場景 | 系統實際用的 marginPct |
|---|---|
| 客戶綁 A 級 | 12%（或負責人自訂）|
| 客戶綁 B 級 | 15%（或負責人自訂）|
| 客戶綁 C 級 | 18%（或負責人自訂）|
| 客戶綁 D 級 | 22%（或負責人自訂）|
| **客戶沒綁**（建議售價算法）| **20%**（hardcoded、不能改）|
| **客戶沒綁**（minPrice 守門）| **null、不啟動守門**（見 §3.4）|

⭐ 換句話說：**沒綁等級的客戶、建議售價有預設 20% 給業務員參考、但守門不啟動、業務員填多低系統都不擋**。

#### §3.7.E 沒 priceX 沒歷史成本怎麼辦

如果**料件主檔 priceX 沒填**、又**沒有 90 天歷史採購紀錄**：

- 系統算建議售價會回傳 0、basis = `no_data_available`。
- 業務員必須手動憑經驗或現場詢價輸入單價。

實務上、伊諾瓦開戶時會幫新客戶把常見料件的 priceA/B/C/D 預先帶值、減少這種「兩邊都沒」的情況。

### 3.8 資料來源 / 資料去向

- 來源：
  - 系統 seed 預設 4 級 + 預設加成率（每個 tenant 都有）。
  - 業務員在往來對象主檔給客戶綁等級。
  - 全版本（含 LITE）負責人可在客戶分級主檔改加成率（⚠️ code 暫鎖、放開後此入口生效）。
- 去向：
  - 報價單每行 minPrice 計算（§3.3）。
  - 銷貨單每行 minPrice 計算（同上）。
  - 銷退單金額沖帳（用銷貨原價、不重算 minPrice）。
  - 報表「業務員讓利統計 / 客戶毛利分析」用。

## §4. 報價單 STEP 2

### 4.1 是什麼

業務員給客戶開「我這幾項賣您多少錢、有效期到 XX 日」的單據、等客戶確認 → 轉成銷貨單。

### 4.2 6 狀態流轉

| 狀態 | 是什麼 |
|---|---|
| **DRAFT 草稿** | 業務員開了單、還沒寄給客戶 |
| **SENT 已寄出** | 已把報價傳給客戶（LINE / Email）|
| **ACCEPTED 已接受** | 被銷貨單採用、自動切此狀態 |
| **REJECTED 客戶拒絕** | 客戶不接受 |
| **EXPIRED 已過期** | 過了「報價有效期」自動切此狀態 |
| **CANCELLED 已取消** | 中途作廢、或被新 SO 取代 |

#### 合法狀態切換

```
DRAFT → SENT → ACCEPTED（被 SO 採用）
           ↓
           REJECTED（客戶拒絕）
           ↓
           EXPIRED（到期）
           
任何狀態 → CANCELLED
```

### 4.3 列表畫面

| 欄位 | 說明 |
|---|---|
| **單號** | 系統自動產（例：`NX04QT0001234`）|
| **客戶** | 從往來對象 C 保養廠 / O 同行挑 |
| **報價日** | 開單日期 |
| **有效期** | 報價有效到哪天（過了會自動切 EXPIRED）|
| **總金額** | 含稅總額 |
| **狀態** | 6 狀態徽章 |

### 4.4 開新報價單

按「**N 新增（鍵盤 N 快捷）**」彈出開單表單：

#### 基本資訊

| 欄位 | 說明 |
|---|---|
| **單號** | 自動產 |
| **倉庫** | 必填、取貨倉（影響 minPrice 用該倉成本算）|
| **報價日** | 預設今天 |
| **客戶** | 必填、從往來對象（C / O）挑 |
| **客戶等級** | 系統自動帶該客戶的綁定等級（也可手動改）|
| **有效期** | 報價過了這天自動 EXPIRED |
| **稅率** | 預設 5%、可改 |
| **幣別** | 預設 TWD、多幣別需多據點模組 |

#### 報價明細（衛星表）

每行：

| 欄位 | 說明 |
|---|---|
| **料件** | 從料件主檔挑 |
| **數量** | 報價量 |
| **單價** | 業務員填、或從料件 priceX 帶 |
| **行小計** | 數量 × 單價（自動）|
| **minPrice**（系統算）| avgCost × (1 + marginPct/100)、見 §3 |
| **belowMinReason**（低於 minPrice 時必填）| 自由文字、稽核用 |
| **isSelected** | 勾選代表此行進總計（沒勾的留參考）|
| **備註** | 自由文字 |

⭐ NEXORA 報價單可以「**列多筆給客戶挑**」、業務員勾 `isSelected` 決定哪幾項算入總計。客戶看了報價後只想買其中 2 項、業務員調整 isSelected 就好、不用刪除其他行。

### 4.5 報價單詳情頁的操作

| 按鈕 | 作用 |
|---|---|
| **編輯** | DRAFT / SENT 狀態才能改明細 |
| **送出** | DRAFT → SENT、把報價傳給客戶（業務員實際傳的是 LINE / Email、系統只切狀態）|
| **產生報價文字** | 跳出可複製文字、貼到 LINE 給客戶（類似採購側「產生詢價文字」、見 NX-MANUAL-03 §5.6）|
| **複製為新單** | 客戶要重新報、建一份新單帶舊明細 |
| **作廢** | 切 CANCELLED |
| **轉銷貨單** | 跳到「新增銷貨單」、本報價明細自動帶過去 |

⚠️ ACCEPTED / REJECTED / EXPIRED / CANCELLED 狀態不能改明細（只能改備註）。

### 4.6 銷貨單採用報價的兩種模式

```
模式 1：整張報價 → 整張銷貨單
   業務員從報價單詳情按「轉銷貨單」、明細整份帶到 SO。

模式 2：多張報價 → 一張銷貨單
   業務員從銷貨單開單畫面按「📜 拉客戶舊報價」、
   彈出該客戶所有未過期的報價單、勾選想拉的行、可混拉多張、補新行。
```

⭐ 模式 2 對長期客戶很實用：客戶之前報過、現在想一次下單多張、業務員直接組合不用重新報。

### 4.7 資料來源 / 資料去向

- 來源：業務員手動建。
- 去向：銷貨單採用（自動 ACCEPTED 結案）、客戶歷史報價查詢（業務員後續加同款客戶時參考）。

## §6. 銷貨單 STEP 3 ⭐ 核心流程

### 6.1 是什麼

整個銷售流程的「正式出貨」單據。報價單一旦變成銷貨單、就會：

1. 算出該客戶的應收帳款（沒收錢前掛在應收上）。
2. 觸發庫存補貨判斷（不夠賣的話走自動調撥或同行調貨）。
3. 開始撿貨 / 包貨 / 配送流程（NX-MANUAL-04 §9 講過手機工作站）。

### 6.2 6 狀態流轉

| 狀態 | 是什麼 |
|---|---|
| **DRAFT 草稿** | 業務員開了單還沒確認 |
| **CONFIRMED 已確認** | 客戶確認下單、**自動調撥已觸發**（系統判斷哪些料件要走同行調貨）|
| **PICKING 撿貨中** | 倉管撿貨員開始去庫位撿貨 |
| **SHIPPED 已出貨** | 包貨完成、送出去了 |
| **INVOICED 已開立** | 發票已開、可串財務應收 |
| **CANCELLED 已取消** | 整張單作廢 |

⭐ 銷貨單**整張單一個狀態**、但**每行有獨立的補貨 / 出貨進度**（見 §6.3 / §6.4、這是 NEXORA 的精細設計）。

### 6.3 行級補貨進度（transferStatus、3 種）

每一行銷貨明細有「補貨來源類型」+「補貨進度」：

#### 補貨來源類型（transferSourceType、4 種）

| 代碼 | 來源 | 說明 |
|---|---|---|
| **S** | 本倉現貨 | 主倉有足夠庫存、直接撿、預設 |
| **T** | 自倉調撥 | 別倉有貨、從別倉調過來（**多據點模組才有用、單倉用不到**）|
| **G** | 同行調貨 | 主倉沒貨、跟同行調來 |
| **B** | 客戶訂單 | 大客戶訂貨、要採購商先承諾預訂（客訂專用、預估價見 §3.7.A）|

#### 補貨進度（transferStatus、3 種）

| 代碼 | 進度 | 說明 |
|---|---|---|
| **P** | 待補 | 該行還沒開始補貨 |
| **I** | 補貨中 | 同行調貨已送、或自倉調撥已開、等貨到 |
| **C** | 補貨完成 | 貨到主倉、可以撿了 |

### 6.4 行級出貨進度（fulfillStatus、5 種）

每一行銷貨明細獨立的「貨在出貨流程的哪個階段」：

| 代碼 | 階段 | 對應動作 |
|---|---|---|
| **W** | 等貨 | 還沒撿貨（補貨還沒完成）|
| **PK** | 撿貨中 | 倉管在撿這行 |
| **PL** | 包裝中 | 撿好了在包貨 |
| **D** | 已出貨 | 包好送出去了 |
| **F** | 已完成 | 客戶簽收（自取確認 / 配送送達 / 寄送確認）|

### 6.5 ⭐ NEXORA 銷貨「混合進度」的設計

一張銷貨單 5 行料件、可能是：

```
行 1：剎車片 × 10、來源 S 本倉現貨、補貨進度 C 補貨完成、出貨進度 F 已完成
行 2：機油濾 × 5、來源 G 同行調貨、補貨進度 I 補貨中、出貨進度 W 等貨
行 3：雨刷 × 20、來源 S 本倉現貨、補貨進度 C 補貨完成、出貨進度 D 已出貨
行 4：機油 × 3、來源 G 同行調貨、補貨進度 P 待補、出貨進度 W 等貨
行 5：輪胎 × 4、來源 B 客戶訂單、補貨進度 I 補貨中、出貨進度 W 等貨
```

每行各走各的、整張單的狀態（§6.2）是「**最大公約數**」：

- 任何一行還在 PICKING → 整張單 PICKING。
- 全部行都 D 已出貨 → 整張單 SHIPPED。
- 等等。

⭐ **為什麼這樣設計**：客戶訂 5 種、3 種立刻能出、2 種要等同行調貨 3 天。業務員可以：

- 先把有貨的 3 種出去（部分出貨）、安撫客戶。
- 缺貨的 2 種等同行調來再補出。
- 不用整單卡住、不用拆兩張銷貨單。

### 6.6 開新銷貨單

按「N 新增」彈出開單表單：

#### 基本資訊

| 欄位 | 說明 |
|---|---|
| **單號** | 自動產（例：`NX04SO0001234`）|
| **倉庫** | 必填、出貨倉 |
| **銷貨日** | 預設今天 |
| **客戶** | 必填、從往來對象（C / O）挑 |
| **配送方式** | P 自取 / D 配送 / S 寄送 |
| **配送地址** | 配送 / 寄送時填、可從客戶送貨地址（NX-MANUAL-02 §8.1 配送分區衛星表）挑 |
| **稅率** | 預設 5% |
| **付款條件** | 從客戶帶（NET30 / NET60 / 預付…）|

#### 開單方式

兩種：

1. **轉報價單**：報價單詳情頁按「轉銷貨單」、明細自動帶。
2. **拉客戶舊報價**：銷貨單開單畫面按「📜 拉客戶舊報價」、勾選混拉多張。
3. **直接開**：自己挑客戶 + 加明細。

### 6.7 同行調貨單怎麼觸發

當銷貨明細有任何一行**主倉缺貨**、業務員可以：

```
1. 在銷貨單詳情頁、那行會顯示「📦 主倉不足、需向同行調貨」
2. 業務員按該行「建立同行調貨單」
3. 跳出「+ 從本 SO 創建 TI」對話框：
   - 選同行（從往來對象 O 同行挑）
   - 勾選哪幾行要走這家同行（可一次多行）
   - 填備註
4. 確認 → 系統：
   - 建一張同行調貨單（TI）、明細帶選中的行
   - 銷貨明細對應行 transferStatus 切「I 補貨中」、tiId 寫入連結
5. 同行送貨來、倉管在「庫存中心 → 同行調貨入庫」（NX-MANUAL-04 §10.1）收貨過帳
6. 收貨過帳 → 銷貨明細對應行 transferStatus 自動切「C 補貨完成」、可開始撿包
```

⭐ 同行調貨單 = NX02 的詢價單延伸（同行詢價類型 SP）+ 進貨入庫一個工作流、但角度從銷貨端發起。

### 6.8 出貨流程連動（連到 NX-MANUAL-04）

銷貨單變成 CONFIRMED 後、會自動產：

```
1. 撿貨單（picking）→ 倉管在手機工作站撿貨（NX-MANUAL-04 §9.3）
2. 撿完 → 自動產包貨單（packing）→ 倉管在手機工作站包貨
3. 包好 → ⭐ 此時系統扣庫存（不是撿貨時扣、避免半途撿一半發現缺料）
4. 包貨單完成 → 自動產配送單（delivery）→ 配送員自取確認 / 司機送達 / 寄黑貓
```

對應銷貨單狀態：

- CONFIRMED → PICKING（開始撿）→ SHIPPED（包完出）→ INVOICED（發票開）

### 6.9 庫存扣除時機（⭐ 重要）

⭐ **NEXORA 庫存實際扣除發生在「包貨完成」**、不是：

- ❌ 撿貨時扣（撿一半發現缺料、可退回不算）
- ❌ 銷貨單 CONFIRMED 時扣（剛確認、還沒實際撿）
- ❌ 配送送達時扣（已經出門了、太晚）

理由：「**包好等於不可逆**」、實際扣最合理。

### 6.10 應收掛帳時機

銷貨單 INVOICED 時、系統自動產一筆應收帳款進財務模組（NX-MANUAL-06）、金額 = 銷貨總額、付款條件依客戶設定。

⚠️ **跟採購單「廠商確認時認列應付」是對稱設計**（NX-MANUAL-03 §6.3）：

| 流程 | 認列時機 |
|---|---|
| 採購單 | 廠商確認接單時、認列應付 |
| 銷貨單 | 發票開立（INVOICED）時、認列應收 |

### 6.11 銷貨單列表畫面

| 欄位 | 說明 |
|---|---|
| **單號** | 自動產 |
| **客戶** | 從往來對象帶 |
| **銷貨日** | 開單日 |
| **配送方式** | P/D/S 圖示 |
| **狀態** | 6 狀態徽章 |
| **總金額** | 含稅總額 |
| **付款條件** | NET30 / NET60 等 |

⭐ 列表可篩選「**有缺貨行**」、業務員看哪些單還卡在補貨。

### 6.12 資料來源 / 資料去向

- 來源：報價單轉、業務員直接開、加購多據點模組後的客戶訂單系統。
- 去向：
  - **庫存**：CONFIRMED 時觸發補貨判斷、包貨完成扣庫存（NX-MANUAL-04 §9.4）。
  - **同行調貨單**：自動產 TI（§6.7）。
  - **撿貨 / 包貨 / 配送單**：自動依序產（NX-MANUAL-04 §9）。
  - **應收帳款**：INVOICED 時掛帳（NX-MANUAL-06）。
  - **報表**：銷售額 / 業務員業績 / 客戶占比（NX-MANUAL-07）。

## §7. 銷退單 STEP 4 ⭐ 串財務章節

### 7.1 是什麼

客戶把貨退回來的單據。從銷貨單觸發、走「業務員開單 → 倉管驗收 → 過帳沖帳」三步驟。

### 7.2 5 狀態流轉

| 狀態 | 是什麼 |
|---|---|
| **DRAFT 草稿** | 業務員開單（客戶反映要退、業務員建單）|
| **INSPECTING 驗收中** | 倉管收到貨在檢查 |
| **POSTED 已過帳** | 驗收完成、依退款方式分流到財務 |
| **REJECTED 駁回** | 倉管驗收發現問題（規格不符 / 數量不對）駁回給業務員處理 |
| **CANCELLED 已取消** | 取消整張單 |

合法切換：

```
DRAFT → INSPECTING → POSTED
              ↓
              REJECTED → 任何階段 → CANCELLED
```

### 7.3 ⭐ 3 種退款方式（returnMethod）

⭐ **NEXORA 銷退「不是只有退錢」**、業務員或客戶可選 3 種退款方式：

| 代碼 | 退款方式 | 系統做什麼 | 串到哪個財務單據 |
|---|---|---|---|
| **R** | 退錢給客戶 | 過帳時自動建一張**銷退折讓單**（NX05 Allowance、type='S'）| **NX-MANUAL-06 §X 折讓單**（之後手動收款沖應收）|
| **D** | 折讓下次採購 | 過帳時自動沖**應收帳款明細**（NX05 ArLedger）| **NX-MANUAL-06 §X 應收帳款**（直接從應收扣金額）|
| **X** | 換新品 | **不沖庫存**、業務員手動再開一張新銷貨單給客戶 | 不串財務、純業務動作 |

### 7.4 ⚠️ R 跟 D 的差別

⚠️ R 跟 D 都是「客戶要求補償金額」、但帳怎麼處理不同：

| 場景 | 用 R 退錢 | 用 D 折讓 |
|---|---|---|
| 客戶要拿錢 | ✅ 開折讓單、之後實際付錢給客戶 | ❌ 沒拿錢、變折扣 |
| 客戶要下次扣 | ❌ 過度麻煩 | ✅ 直接從應收扣 |
| 帳上狀態 | 應收沒變 + 多了一張折讓單欠款給客戶 | 應收直接變少 |
| 適合場景 | 客戶已付款、要實際退錢 | 客戶還沒結帳、下次抵 |

⭐ 業界常見：客戶月結客戶 → 用 D 折讓（下次帳單抵）；現金客戶 → 用 R 退錢。

### 7.5 X 換新品的特殊處理

⭐ **X 跟 R/D 完全不同**：

- 客戶反映瑕疵、想要新品換、不是要錢。
- 客戶可能還沒把瑕疵品退回、或不退（廠商勘驗用照片就好）。
- 系統 X 走法：
  - **不沖庫存**（沒實際收貨）。
  - **不串財務**（沒退錢 / 沒扣應收）。
  - 業務員自己手動建新銷貨單給客戶（補貨）。
  - 瑕疵品的後續處理由業務員自行決定（自家內訴開保固單、或要求客戶寄回）。

⚠️ 後續軌規劃可能自動建新 SO、目前要手動。

### 7.6 開新銷退單

業務員從銷貨單詳情頁按「**+ 建銷退單**」、彈出開單表單：

| 欄位 | 說明 |
|---|---|
| **單號** | 自動產 |
| **來源銷貨單** | 從哪張 SO 退、自動帶 |
| **銷退日** | 預設今天 |
| **退款方式** | R / D / X 三選一 |
| **退貨明細**（衛星表）| 從來源 SO 帶可退項、業務員勾選哪幾行 |

每行明細：

| 欄位 | 說明 |
|---|---|
| **來源 SO 行** | 對應原銷貨單的哪一行 |
| **料件** | 自動帶（snapshot）|
| **數量** | 退貨量（不能 > 原銷量）|
| **退貨原因** | 必填、自由文字（例：「客戶反映異音」）|
| **單價** | 原銷貨單價 |
| **行小計** | 數量 × 單價 |
| **讓利原因** | 退款金額跟原銷售金額有差時的補充說明 |

### 7.7 倉管驗收（INSPECTING 階段）

業務員送出 DRAFT → 切 INSPECTING、倉管在工作站接到通知：

```
1. 客戶送回 / 司機收回 / 客戶郵寄回
2. 倉管拆箱、逐件檢查
3. 每行勾「處置旗標 dispositionFlag」：
   - G 好品 → 入主倉、可再賣
   - B 壞品 → 寫進「異常回報」表（NX-MANUAL-04 §7）等後續處置
4. ⚠️ 必須每行都勾完才能過帳
5. 過帳 → 狀態切 POSTED
```

⭐ **R/D 過帳會做的 4 件事**：

```
1. 庫存帳：好品（G）入主倉、壞品（B）不入庫直接寫異常表
2. 自動建 NX05 Allowance 折讓單（type='S'、即銷退折讓）
3. 依 returnMethod 分流：
   - R → 折讓單獨立、等之後實際付錢給客戶（走收付款）
   - D → 折讓單自動沖應收帳款明細（ArLedger）
4. 自動建 NX06 RETURN_PICKUP 退貨配送單草稿（如果客戶有送貨地址、用於下次去客戶處收貨）
```

⭐ **X 過帳會做的事**：

```
1. 跳過庫存帳（沒實際收貨）
2. 跳過折讓單
3. 業務員手動建新 SO 給客戶
```

### 7.8 退貨配送單 RETURN_PICKUP 自動建

⚠️ 重要邊界揭露：

- R/D 過帳時、系統會檢查客戶有沒有送貨地址（往來對象 §配送分區衛星表）。
- 有 → 自動建 NX06 RETURN_PICKUP 配送單草稿、下次司機去客戶處收貨。
- 沒地址 → 跳過、不建配送單（不報錯）。

### 7.9 跨手冊串接點（⭐ 留意 NX-MANUAL-06 一致性）

⚠️ Stop 1 §3.6 + NX-MANUAL-04 §7.7 提到過：「折讓單自動沖應付」邏輯目前**從採購側保固單**（NX-MANUAL-03 §9.9）跟**銷貨側銷退**兩條路徑都會匯到 NX05 Allowance 模組。

- 採購側：保固單結果 = REF + 方式 = A → 自動建 DRAFT 折讓單沖應付（NX-MANUAL-03 §9.9）。
- 銷貨側：銷退單 returnMethod = R → 自動建 Allowance 沖應收（本節 §7.7）。

兩條路徑都會在 NX-MANUAL-06 §X 折讓單章節整合對齊。**目前是不同 allowanceType**：

- 保固 REF + A 折讓：type = 'P'（PR/採購折讓）。
- 銷退 R/D：type = 'S'（SR/銷退折讓）。

兩種 type 在 NX-MANUAL-06 會詳細整合說明。

### 7.10 資料來源 / 資料去向

- 來源：客戶反映退貨、業務員從原銷貨單觸發開單。
- 去向：

  - **財務**：R/D 自動建折讓單沖應收（NX-MANUAL-06）。
  - **配送**：R/D 自動建退貨配送單（NX-MANUAL-06 配送或下游模組）。

## §8. 客戶等級變更核可

### 8.1 是什麼

業務員發現某客戶該升 / 該降等級（例：B 級客戶最近量大、應升 A 級享更低毛利）、提出變更申請、要負責人核可才生效。

### 8.2 為什麼要核可

⭐ 客戶等級直接影響毛利（§3.2）：

- 從 B 級（marginPct 15%）改 A 級（12%）→ 之後所有報價 / 銷貨自動帶較低售價 → 公司毛利減少。
- 一個業務員順手降級客戶 = 直接給公司打折、所以**要負責人核可**。

### 8.3 3 狀態流轉

| 狀態 | 是什麼 |
|---|---|
| **PENDING 待核可** | 業務員送出、等負責人決定 |
| **APPROVED 已核可（已生效）** | 負責人核可、客戶等級實際換掉、之後新單套新等級 |
| **REJECTED 已退回** | 負責人駁回、客戶等級不變、業務員看到退回原因 |

### 8.4 操作流程

```
業務員：
   1. 從客戶主檔詳情頁、按「申請變更等級」
   2. 選新等級（A/B/C/D 中選一個非現有的）
   3. 填變更理由（必填、稽核用）
   4. 送出 → 狀態 PENDING

負責人：
   5. 從首頁公告 / 任務 / 通知看到「等級變更待核可」
   6. 進「客戶等級變更歷史」工作頁、看詳情
   7. 點「核可」→ 狀態 APPROVED、客戶等級立刻換、之後新單套新等級
      或 點「退回」+ 填退回理由 → 狀態 REJECTED、客戶等級不變

業務員：
   8. 從通知收到結果
   9. 已生效的 → 開新單會自動套新等級
      被退回的 → 看退回理由、視情況重新申請
```

### 8.5 變更歷史記錄

每次變更（核可 / 退回都算）都會留歷史紀錄：

| 欄位 | 說明 |
|---|---|
| **單號** | 自動產 |
| **客戶** | 哪個客戶 |
| **舊等級 → 新等級** | 從 X 到 Y |
| **狀態** | PENDING / APPROVED / REJECTED |
| **申請人 / 申請時間** | 業務員 + 時間 |
| **申請理由** | 業務員填的 |
| **核可人 / 核可時間** | 負責人 + 時間（APPROVED 才有）|
| **退回理由** | 負責人填的（REJECTED 才有）|

### 8.6 資料來源 / 資料去向

- 來源：業務員從客戶主檔詳情頁按「申請變更等級」觸發。
- 去向：
  - 核可後 → 改往來對象主檔 customerGradeId、之後新單走新等級。
  - 報表「客戶等級變動史」用、稽核用。

### 10.3 系統自動算建議售價的功能


### 10.4 業務員建議的售價維護節奏
