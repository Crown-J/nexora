# NEXORA GRID v3.0.0 外殼規格

## 0. 這份文件是什麼

**兩百多個頁面，只用六支外殼。**

本文定義那六支殼各自是什麼、長什麼樣、⛔ 不能放什麼。
新頁面一律從這六支挑一支，⛔ 不再各做各的。

- 上位依據：`docs/專案/介面規格/NEXORA-介面架構-v3.0.0.md`（畫面骨架 · 九宮格 · 視覺與鍵盤規範 · 手機分工）
- 判斷已作廢的舊設定：`docs/_team/已作廢決策清單.md`
- 設計借鏡：`docs/_team/design-references.md`

### 怎麼推導出來的

⛔ **不是從資料表推的，是從「使用者一天中的時刻」推的。**

> 頁面存在 ≠ 有人用。分析單位是**時刻**，不是頁面。

每個頁面問三題：① 對應到誰一天中的哪個時刻？② 那個時刻他手上有什麼、要拿到什麼？
③ 同一個時刻是不是散在好幾頁？

答不出①就不是時刻（例：「管理員要維護客戶分級」——一年一次，那不是時刻）。

**已驗證兩個角色**（2026-08-02）：

| 角色 | 時刻數 | 現有頁數 | 收斂後 | 用到幾支殼 |
|---|---|---|---|---|
| 銷售作業 | 13 | 44 | ~10 | 5（⛔ 無現場殼） |
| 倉庫作業 | 13 | 48 | ~12 | 5（⛔ 無開單殼） |

⭐ 兩個角色的工作性質差最遠（一個坐位子、一個戴手套），**六支都夠用、⛔ 不需要第七支**。

## 2. 通用原則（六支全部適用）

### 2.1 ⭐ 先結論，後細節

這是「電商化」的本體，⛔ 不是圓角和留白。

| | 傳統 ERP | NEXORA |
|---|---|---|
| 資訊順序 | 先給 30 個欄位 → 你自己判斷 | **先給一句結論** → 想知道細節才展開 |

**六支殼全部套這一條。** 卡片只是實現手段之一——清單頁一樣可以先給結論（狀態欄放最左、逾期整列染色），⛔ 不必把每一列變成卡片。

### 2.2 卡片與表格的分界

| 工作性質 | 用什麼 | 為什麼 |
|---|---|---|
| **看懂、做決定** | 卡片 | 一次一個判斷，留白幫助聚焦 |
| **一次處理很多筆** | **表格** | 一屏要看到 20＋ 筆才能比對 |
| **一天重複幾百次** | **表格** | 每筆多滑一次＝一天多滑幾百次 |

⚠️ **歷史教訓（2026-06-24）**：卡片式主檔範式被推翻過一次，12 個主檔試套後全退回表格。
事後判讀：失敗主因**很可能是只換了 12 頁**（12 頁卡片、46 頁表格＝視覺不統一）。
但字典型主檔（國家 6 筆、幣別 4 筆）本來就不該卡片化——那是「一次看很多筆」的工作。

### 2.3 ⚠️ 借視覺，⛔ 不借互動模型

參考清單（Stripe / Linear / Notion / Shopify / AWS Billing）**全部是滑鼠導向產品**，
沒有一個能純鍵盤跑完。直接照抄會撞上：

- 介面架構 §1「熟手只記快捷鍵，不看選單」
- 介面架構 §7.2 驗收條件「整頁拔掉滑鼠做得完」

**可以借**：間距與字重做層次（⛔ 不用線框）· 結論放最上面 · 側邊抽屜取代開新頁 · 左主體右附屬並排
**⚠️ 有條件借**：Linear／Notion 的「點擊即編輯」——**只可用於主檔與草稿**，
　　　　　　　⛔ **過帳後的單據不適用**（直接改欄位＝沒有稽核軌跡）

### 2.4 修改分兩種

| 你在改什麼 | 走哪裡 |
|---|---|
| **還沒生效的單**（草稿報價、未確認銷貨） | 回**開單殼**繼續走。它本來就沒完成，不是「修改」是「接著做」 |
| **已生效的單**（已出貨、已過帳） | ⛔ **不可直接改欄位** → 走**檢視殼**「加一個動作」 |

⭐ 理由：本系統的命脈是「可信可稽核的帳、過得了 COSO」。直接改欄位跟這件事直接衝突。
做法同電商——你下單後不能編輯訂單，只能「申請改地址」「申請取消」，**每個修改都是一筆有紀錄的動作**。

### 2.5 ⭐ 全域搜尋不是一支殼

**最高頻的動作是「打一個東西進去、立刻得到答案」**，它⛔ 不該是頁面。

一個搜尋框永遠在（工作檯上、頂列也有），打進去右邊直接出答案。
**同一個搜尋框，依角色回不同答案**：

| 角色 | 打料號進去，要什麼 |
|---|---|
| 業務 | 價格（市場行情價＋公司定價）＋有沒有貨＋這客戶上次買多少 |
| 倉管 | 在哪個庫位＋還有幾個 |
| 採購 | 進價＋過去三個月銷量＋上次進價 |

⚠️ 做成頁面是退步——業務接電話時⛔ 不該還要先想「我要去哪一頁」。
（介面架構 §3.3 已規定搜尋框永遠聚焦，本條是它的延伸。）

### 2.6 就地新增

微量主檔（實測 15 張表共 89 筆資料）⛔ 不配獨立頁面。
選客戶時發現沒有這個分級 → **當場打字新增**，⛔ 不必離開現場。

⚠️ 代價：誰都能新增＝分級表會長出「A級／a級／甲級」三種寫法。
**必須配**：權限閘 ＋ 事後審核清單（主管工作檯出現「這週有人新增了 3 個客戶分級，要確認嗎」）。

## 3. 殼 1 · 工作檯

| | |
|---|---|
| **職責** | 今天要做的事自己送上門，⛔ 使用者不必學會找功能 |
| **落點** | 登入落點 · 🏠 分頁（關不掉） |
| **對應時刻** | 銷售「開工看今天要做什麼」· 倉庫「看今天的量」· 全角色 |
| **現況** | ✅ **已上線**：`/dashboard` ＝ `design/layout/v3/V3Workbench.tsx`（接 `getHomeSummary`）。<br>⚠️ 另有一支 `WorkbenchTemplate`（119 行）**生產 0 頁**——兩支重複，待收斂。<br>⚠️ **缺「內容依角色組成」**：現在所有人看同一份（業務看得到待撿貨、倉管看得到逾期應收）。<br>　卡在登入權限已拔掉、沒有角色可分；`MeDto.roles` 有欄位，等權限接回來才做得了。 |

### 佈局

1. **搜尋框永遠聚焦**——進系統就能直接打料號（客戶隨時來詢價是常態）
2. **只有三塊、數字要大**
3. **點數字直接進清單**，⛔ 不必先選日期或條件

### ⛔ 禁止

- ⛔ 不放圖表（長輩看數字比看圓餅圖快）
- ⛔ 不做「自訂儀表板」——每個角色出廠就是對的樣子

⭐ 這頁是九宮格能收起來的前提：**日常 90% 在這一頁解決。**

## 4. 殼 2 · 清單

| | |
|---|---|
| **職責** | 查、比對、挑一筆進去 |
| **對應時刻** | 銷售「查一張既有的單」· 倉庫「倉庫單據」· 所有主檔列表 |
| **現況** | `ListTemplate`（237 行）已寫，**生產 0 頁**。實際在跑的是舊的 `MasterTable`(555)＋`ErpToolbar`(632)，**27 頁共用** |

### 佈局

- 表頭 14px / 內文 15px（⚠️ 一般 ERP 是 12–13px，對年長使用者太小）
- 預設只顯示 6–8 欄，其餘收進「欄位」面板。⛔ 不靠縮小字級塞更多欄
- ⛔ 不用灰字當主要內容——老花看灰字最吃力，muted 只給次要說明
- **狀態欄放最左**，異常整列染色（＝§2.1 先結論）

### ⭐ 主篩選按「狀況」，⛔ 不按單別

業務問的是「哪些還沒結束」，⛔ 不是「哪些是報價單」。

```
狀況：[進行中 12] [等客戶回 5] [要出貨 8] [有問題 2] [全部]     ← 主篩選
單別：●全部 ○報價 ○銷貨 ○退貨 ○調貨                          ← 次篩選、按 1～5 切
```

- **關聯鏈縮排顯示**：一張報價轉出的銷貨掛在它下面
- **狀態寫人話**：「等客戶回 · 3 天」，⛔ 不是「DRAFT」「PARTIAL」
- 預設只看進行中，歷史要按「全部」

### 鍵盤

`↑↓` 移動 · `Enter` 開啟 · `Home/End` 首末列 · `Tab` 可進出表格 · 數字鍵切次篩選

### ⛔ 禁止

- ⛔ 不做卡片式（一屏要看到 20＋ 筆）
- ⛔ 不做只有滑鼠能觸發的操作
- ⛔ 全程不加 transition／animation

### ⭐ 一頁多入口（號碼凍結的解法）

四個舊入口各帶不同預設篩選、進**同一頁**；另撿角色的空號當不篩的入口。
⛔ 九宮格號碼一格都不動（介面架構 §5 號碼凍結鐵則）。

## 5. 殼 3 · 檢視

| | |
|---|---|
| **職責** | 打開一筆的全貌 ＋ **現在可以做什麼** |
| **對應時刻** | 銷售「查客戶全貌 / 單子出狀況 / 對帳 / 保固」· 倉庫「單據檢視 / 零件庫存檢視」 |
| **現況** | ⛔ **完全沒有**。28 個動態明細頁各做各的 |

⭐ **六支裡唯一全新的一支，也是電商化收益最高的一支。**

### 佈局

```
┌────────────────────────────────────────┐
│ SO-0012　大安汽車              [已出貨] │  ← 主體 + 狀態
├────────────────────────────────────────┤
│  金額 48,200 │ 毛利 9,140 │ 應收 48,200 │  ← ⭐ 三個關鍵數字，先給結論
├────────────────────────────────────────┤
│ 明細 │ 出貨 │ 帳款 │ 歷程              │  ← 細節收在頁籤，要看才展開
└────────────────────────────────────────┘
[ 轉銷貨 ] [ 申請退貨 ] [ 改地址 ] [ 作廢 ]   ← ⭐ 動作列
```

- **左主體、右附屬並排不分頁**（Shopify 訂單詳情範式）——複雜明細用**側邊抽屜**，⛔ 不另開頁
- 同一支殼套三種主體：**單據** · **客戶／供應商** · **零件**

### ⭐ 動作列＝修改的唯一入口

已生效的單⛔ 不可直接改欄位（§2.4）。動作列例子：

| 主體 | 動作 |
|---|---|
| 報價 | **轉銷貨**（⛔ 現在沒有） · 重新寄送 · 作廢 |
| 銷貨 | 申請退貨 · 改送貨地址 · 作廢 |
| 客戶 | 調整等級 · 新增聯絡人 · 加入拜訪紀錄 |

### 樹狀結構圖

據點架構圖 · 組織架構 · 角色檢視三頁**歸本殼**（一個主體＋一張結構圖）。
⛔ 不為三頁多養一支殼（執行長 2026-08-02 拍板）。

## 6. 殼 4 · 開單

| | |
|---|---|
| **職責** | 一步步完成一張新單，**每段只問一件事** |
| **對應時刻** | 銷售「成交 / 正式報價 / 找貨 / 新客建檔」 |
| **現況** | `FlowTemplate`（464 行）＋ `FlowPanes`（121 行）·**生產 2 頁**（建立報價、建立銷貨單） |

### ⭐ 為什麼是流程型，⛔ 不是單據型

| | 傳統單據模板 | 流程型 |
|---|---|---|
| 呈現 | 40 個問題同時攤開 | **每段一個明確的問題** |
| 使用者反應 | **狂按 Enter 跳過去**，該填的塞進備註 | 走到那一段，畫面只問那件事 |
| 後果 | 用久了嫌麻煩 → 反而要求外掛「即時報價」 | — |

⭐ **恆迎實證**：明明有「取貨方式」欄位，使用者偏偏都打在最後的備註說「這客戶要自取」。
`DocTemplate`（247 行）已作廢，生產 0 頁使用。

### 欄位存廢的判準

> **每個欄位都要能回答「這格空白的話，誰會受影響」。**

答不出來的⛔ 不該出現在流程裡。答得出來的（取貨方式 → 倉庫要不要備出貨、司機要不要排班）
⛔ 不該是單頭一格下拉選單，**該是流程裡自己的一段**。

### 鍵盤（開單是打字工作，⛔ 不能要求碰滑鼠）

- 每一格就是輸入框，**直接打**——⛔ 不做「先選取再按 Enter 進編輯」那一套
- `Tab / Shift+Tab` 前後 · `↑↓` 同欄上下 · 最後一格 `Tab` 自動新增一列
- `Enter` 進右欄屬性面板 · **跳段一律走 `Alt`**
- `Ctrl+Delete` 刪目前這列

### ⚠️ 老手模式（待驗證）

五段流程對「一天開兩三張」很好，對「一天開兩百張」是災難（每張多按四次跳段）。
⚠️ **待確認亞羅實際單量**——上百張的話本殼要加「一屏攤開、Tab 直接跑到底」的老手模式。

### 兩條路都要留

| 路 | 流程 | 現況 |
|---|---|---|
| **A** 先報價、之後成交 | 查價 → 正式報價 → 等客戶回 → **在報價上按「轉銷貨」** | ⛔ 最後一步沒有（→ 檢視殼動作列） |
| **B** 當場就買 | 查價 → 直接開銷貨單（開單時可「拉報價」補進來） | ✅ 後端已完成 |

兩條路共用同一段「收品項」的邏輯（已抽成共用模組），**差別只在停在哪一步**。

## 7. 殼 5 · 現場

| | |
|---|---|
| **職責** | 手上有東西，掃碼、確認、下一件 |
| **對應時刻** | 倉庫「撿貨 / 包貨 / 出貨 / 驗收 / 上架 / 盤點」· 物流「配送 / 簽收 / 代收貨款」 |
| **現況** | ⛔ 沒有統一外殼。但**條碼掃描共用元件已完成**（CODE128／EAN／QR／Code39／UPC，iOS＋Android 已驗） |

### ⭐ 現場殼 vs 開單殼

> 兩者都在收集資訊產出單據，差別是：
> **開單殼是「回答問題」，現場殼是「完成手上的事」。**
> 倉管⛔ 不覺得自己在開單，他覺得自己在點貨——但系統產出的是一張進貨單。

### ⭐ 一支殼 · 一個路由 · 三套佈局

⛔ **不另開手機路由**（執行長 2026-08-02 拍板）。

| 佈局 | 裝置 | 誰用 | 一次處理 | 輸入 |
|---|---|---|---|---|
| **走動** | 手機 | 撿貨、上架 | **一件** | 相機掃碼＋大按鈕（戴手套按得到） |
| **定點** | 固定螢幕 | **收貨區／包貨台／出貨台** | **一箱／一單** | 掃描槍（等同鍵盤）＋鍵盤 |
| **看板** | 電腦 | 倉管主管 | **看全部** | 鍵盤滑鼠 |

⚠️ 定點與看板在瀏覽器眼裡是同一種裝置，**分不出來會出事**（主管看到執行畫面、包貨員看到看板）。

### ⭐ 工作站機制

**綁在螢幕上，⛔ 不是綁在人身上。**

- 那台螢幕**第一次開機問一次**「你是哪個站？」，選了記住
- 之後開機直接就是那個站的樣子，⛔ 不用每天登入選
- 理由：那台螢幕⛔ 不會被拿去做別的事

**記在瀏覽器本機儲存，⛔ 不動 schema**（介面軌紀律：⛔ 不碰 schema／API／DB）。

⚠️ 代價：換瀏覽器或清快取要重選。系統⛔ 不知道「哪一台包的」，只知道**誰**包的（使用者本來就有記錄）。要稽核到機台再加表不遲。

**三種定點站**：收貨區 · 包貨台 · 出貨台（執行長 2026-08-02 拍板，收貨區要）。

### ⭐ 規模⛔ 不是設定

⛔ **不做「小規模／大規模」選項或設定精靈。**

| 沒有任何螢幕註冊成工作站 | 有螢幕註冊了 |
|---|---|
| 全部走手機 → **自動是單人作業** | 那台是定點版 → **自動是多工作線** |

同一套程式碼跑兩種規模：沒有開關、沒有版本、⛔ 沒有人會選錯。
一個租戶可以大倉小倉並存，成長時⛔ 不用「切換模式」。

⭐ 這跟產品鐵則同一個精神——⛔ 不做功能閘門，能力自己長出來。

### ⭐ 池模型同時解決兩種規模

後端已完成：**撿貨池** 9 個端點（含放回／取消撿／暫存出庫）· **包貨池** 13 個端點（含裝箱／併包／封箱）。

| 規模 | 池怎麼運作 |
|---|---|
| **多工作線** | 撿的人撿完丟進池 → 包貨台從池裡撈。**這就是交接，⛔ 不需要人對人喊** |
| **單人作業** | 池裡永遠只有自己剛撿的那批，同一支手機接著做，**他感覺不到池的存在** |

### ⭐ 介面可合併，帳⛔ 不能合併

單人模式下撿→包→出是連續動作。強迫走三段、每段確認，一天多按幾百次
→ 他就會想辦法跳過，恆迎那個「用久了嫌麻煩」的病又長回來。

**做法**：單人模式「一鍵封箱出貨」一個按鈕做完，但系統背後**照樣寫三段紀錄**。
理由：帳要可稽核，而且他長大變多工作線時歷史資料是連續的、⛔ 不用轉檔。

### ⚠️ 條碼掃描是彈窗的第四種例外

相機預覽本來就得吃滿畫面。列為介面架構 §2.1 的**第四種例外**
（前三種：確認對話 / 挑選器 / Toast）。執行長 2026-08-02 拍板。

### 同源合併

**驗收三種合一**（進貨 / 調撥 / 銷退）——來源不同但動作一樣（點貨、對數量、判良品）。
做三頁是照資料表切，⛔ 不是照人的工作切。**來源當篩選。**
