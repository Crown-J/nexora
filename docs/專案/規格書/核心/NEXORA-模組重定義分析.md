## 1. 核心產出：三層架構模型

討論收斂出一個關鍵區分——過去把「模組」「能力」「流程」混成一件事，這是苦惱的根源。正確拆成**三層**：

| 層 | 定義 | 例子 | 白話 |
|---|---|---|---|
| **① 模組** | 擁有一組資料表 ＋ 一組能力的**靜態單位** | 銷售、進貨、庫存、總帳 | 一個房間，界線清楚、別人不越界改它的表 |
| **② 共用能力** | 被多個劇本叫用的**動作** | 撿貨／包貨／出庫／入庫（庫存擁有）| 房間裡的一種本事，誰都能來借用 |
| **③ 劇本** | 穿過多個模組的**生意情境** | 正常銷售、調撥、同行調貨、銷退 | 一條路線，穿過好幾個房間，每個房間做自己那段 |

### 1.1 為什麼要拆這三層（解掉的兩個苦惱）

- **苦惱 A：同行調貨牽扯進貨採購、塞不進一個抽屜。**
  解：它**不是模組，是劇本**。拆開＝銷貨單缺貨觸發（銷售）→ 跟同行取得料（進貨）→ 入庫（庫存）→ 撿貨出貨給客人（庫存＋銷售）→ 付同行/收客人（總帳）。它穿過四個房間，每個房間做自己那段。**現況已用「銷貨單↔調貨單↔進貨驗收」三單自動回寫鏈實作，本來就跨模組——只是沒命名。現在命名它：劇本。**

- **苦惱 B：撿貨包貨送貨到底歸銷售還是庫存？**
  解：撿包送是**庫存模組的共用能力**，銷售只是叫用它的其中一個情境。證明＝調撥（倉A→倉B）沒客人沒銷售，一樣要撿包送。所以撿包送歸庫存；銷售、調撥、同行調貨、銷退都只是來借用的劇本。

### 1.2 鐵律：模組擁有資料，劇本編排流程

- 一個**模組**＝一組它獨佔、負責的表（銷售管 So/SoItem/Quote…，別人不准直接寫）。**不是**「一模組一張表」——一張單天生是「單頭＋單身」多表（一張銷貨單 = 1 筆 `Nx04So` ＋ N 筆 `Nx04SoItem`），逃不掉。
- 一個**劇本**＝跨模組的編排，靠**單據串接**把各模組那一段接起來（現況 `Nx98DocLink` 已在做單據關聯）。
- 治偉盟病的正解不是「一張表」，是「**模組界線清楚、劇本用單據串、狀態＋外鍵把正確寄託在資料庫結構上**」。

## 2. 循環 ＋ 行業皮：兩套框架怎麼疊

策略骨架 §3/§6 講「會計師版九大循環」、§5 講「ERP 實務清單」——兩者對不上，是因為**不在同一層**。正確疊法：

```
        ┌──────────── 財報 IFRS/TIFRS（對外通行證）────────────┐
        │      總帳脊椎：分錄 → 傳票 → 日記帳 → 總分類帳 → 試算表    │ ← 所有循環匯流的終點
        └──▲──────────────────▲────────────────────▲──────────┘
           │                  │                    │
    ┌──────┴───────┐   ┌──────┴───────┐    ┌───────┴──────┐
    │ 銷售及收款循環 │   │ 採購及付款循環 │    │ 薪工循環（後）│   ← 橫軸：循環＝模組
    │  內含 應收子帳 │   │  內含 應付子帳 │    │              │
    └──────┬───────┘   └──────┬───────┘    └──────────────┘
           │      存貨子帳（＝庫存，兩循環共用）      │              ← 子帳/共用能力，非獨立循環
           └───────────────┬──────────────────────┘
             ┌─────────────┴─────────────┐
             │  主資料平面：客戶/供應商/科目表/倉庫  │                ← 每個循環都讀的參考層
             └─────────────┬─────────────┘
                    ┌───────┴────────┐
                    │  汽配行業包（插件） │                          ← 縱軸：行業皮，可抽換
                    │ 料號/車型/VIN/SOP │
                    └────────────────┘
```

**身分歸位**：§5 清單的七個東西分屬三種身分——
- **循環**（真循環，各自有內控）：銷售收款、採購付款。
- **子帳 sub-ledger**（明細帳，餘額匯總過一筆到總帳控制科目）：應收（掛銷售循環）、應付（掛採購循環）、存貨（兩循環共用）。
- **脊椎**（匯流終點，非循環）：總帳／財報。

**核心 vs 行業皮兩把尺，不能混成一把**：
1. 核心 vs 行業（所有產業都要 vs 某產業才有）
2. 主幹道 vs 逃生門（80% 日常單 vs 例外變體）
同行調貨＝「銷售循環裡的一個逃生門」，用核心零件拼出、只有薄薄一層汽配味——不是厚重的新模組。**行業皮要薄。**

## 4. 缺口分析（grep 實測、精確計數）

### 🛠 缺口 1（第一優先・命脈）：總帳脊椎是空的

grep 找 journal/voucher/分錄/總帳/試算表/財報 → **0 個 model**；唯一「借貸」字眼是 `creditLimit`（授信額度，與簿記無關）。

NX05 現有 10 張表全是**子帳與操作**（科目表、應收/應付明細、折讓、票據、收付款、關帳），**有子帳但子帳不過分錄進總帳，也無財報結構**。

- 這是策略骨架 §8 指的第一缺口，「可信財報＝國際通行證」整個 vision 的命根。
- **性質＝加新房間、不拆舊牆**（additive），符合 §4「加模組不是重造引擎」。
- **要做的核心工作**：定義「過帳事件 → 借貸分錄樣板」對照表，例如
  - 銷貨確認 → 借:應收帳款／貸:銷貨收入 ＋ 貸:銷項稅額
  - 出貨扣庫存 → 借:銷貨成本／貸:存貨
  - 收款 → 借:銀行存款／貸:應收帳款
  - 進貨驗收 → 借:存貨 ＋ 借:進項稅額／貸:應付帳款
- 新增表（規劃、未定）：傳票單頭、分錄行（借貸）、總分類帳科目餘額、試算表、財報結構。

### 🛠 缺口 2（第二優先・不急）：行業皮織進核心主檔

NX01 的 63 張表裡，汽配專屬（`Part`/`PartOemCode`/`Model`/`PartModel`/`PartCompatGroup`/`PartKit`/`Brand`）**與中性主資料（Country/Currency/User/Warehouse/Partner）混坐同一模組**，違反 §4「插件不得織進核心」。

- ⚠️ **待深驗**：目前只確認「坐在一起」（同模組），**尚未確認核心邏輯有沒有焊死**（過帳/查詢有無寫死「一定有車型」的假設）。坐在一起好拆、焊死難拆，成本差很多——**抽皮前必先深驗焊死深度**。
- **不急的理由**：第一個客戶就是汽配（恆迎/亞羅），皮織在核心不傷他，只傷將來換五金/機車料皮。按 §7「別太早擴張」，排在總帳之後。

### 🧹 缺口 3（最後做・整潔）：NX01 是雜物間

63 張表混了六種東西：主資料 ＋ 權限(Role/Permission/View) ＋ 公告(Bulletin) ＋ KPI ＋ 行政(Calendar) ＋ 地址(City/District/Street) ＋ 汽配。違反「一個模組界線清楚」，但屬**組織整潔、不擋 vision**，最後拆。

### 關於「循環命名（NX01→循環模組）」
換招牌、非改結構。重要結構在現招牌下已對，換名不推進 vision 卻要冒重構風險。**放最後**——等總帳蓋好、行業皮抽完，自然水到渠成再換。

## 5. 動工順序建議

| 優先 | 做什麼 | 性質 | 依據 |
|---|---|---|---|
| **1️⃣ 命脈** | 補總帳脊椎（事件→分錄樣板 ＋ 傳票/日記帳/總帳 ＋ 試算表 ＋ 財報結構）| 加新房間，不破壞既有 | 缺口 1、策略骨架 §6 硬事實 |
| 2️⃣ 架構 | 抽行業皮出核心（**先深驗焊死深度**再決定怎麼拆）| 有風險，第一客戶不急 | 缺口 2、§4 鐵律 |
| 3️⃣ 整潔 | NX01 雜物間拆分 ＋ 循環命名 | 換招牌，最後做 | 缺口 3 |

**一句話收斂**：架構不用重打、引擎是好的；把空的總帳脊椎補起來，才是現在真正要做的事。

### 附：本份的討論推導線（2026-07-22）

九大循環哪九個（會計師版 vs §5 ERP 版對不上）→ 兩者不同層、疊三層解掉 → 進銷存該不該一個模組（對在耦合、錯在邊界＝偉盟病）→ 三模組切法（銷售銷退/進貨採購/出庫入庫）→ 一模組一張表做不到（單頭單身鐵律）→ 同行調貨塞不進一個抽屜（苦惱 A）＋ 撿包送調撥也要（苦惱 B）→ **關鍵突破：模組 vs 共用能力 vs 劇本 三層拆分** → 兩苦惱同時解、行業皮變薄 → grep 盤現況 → 引擎大多已對、真正缺總帳脊椎 → 不用重打、補房間。**全線自洽。**
