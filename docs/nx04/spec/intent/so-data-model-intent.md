## 1. 業務目標

NEXORA 從「SOP 流程式 UI」轉向「5 工作台動作式 UI」。SO 資料模型必須支援：

- **超賣**：業務在電話上立即接單，即使本倉庫存不夠
- **結構化補貨**：每筆超賣必須綁定明確的補貨來源（自倉調撥 / 同行調貨 / 客戶訂單），不允許自由文字
- **雙帳追蹤**：物理庫存 vs 業務承諾分離，可反查負庫存來源
- **彈性出貨**：一張 SO 可拆多張包貨單與送貨單（依包裝體積）
- **明細獨立進度**：每個 lineItem 有自己的補貨進度與出貨進度，不綁整張 SO

設計目標一句話：**支援「受控的超賣」+ 「結構化補貨」+ 「雙帳追蹤」**。

## 2. 5 個關鍵業務概念

### 2.1 結構化的補貨來源

業務在新增 SO 明細時，每項都必須有明確的「**這個明細的貨從哪來**」。

四種來源：
- **本倉夠**：庫存夠，直接出
- **自倉調撥**：本倉不夠，從別的倉調過來（例：從總倉 Z00 調到台北倉 Z01）
- **同行調貨**：自家所有倉都不夠，跟同行買（例：跟同行 D-O104 調）
- **客戶訂單**：當下沒貨也補不到，先記著等補貨（CO）

業務選了「自倉調撥 - Z02」後，系統要**自動建調撥單**通知倉管。
業務選了「同行調貨 - D-O104」後，系統要**自動建詢價單**通知採購。
業務選了「客戶訂單」後，系統要**自動建 CO 單**追蹤。

關鍵：「**選哪一種**」必須是結構化選項（下拉選單），不是 free text。

#### 邊界補充：補貨單的兩種來源（v1.1 補）

這份意圖文件 §2.1 描述的是「**業務送 SO 觸發補貨**」這條 path。但同樣的補貨單（ST 調撥 / TI 同行調貨 / CO 客戶訂單），實際業務上有兩種來源：

1. **SO 觸發**：由 translator 自動建，必有對應 SO line item（`sourceSoItemId` 必填）
2. **手動發起**：倉管 / 採購主動建，沒有對應 SO line item（`sourceSoItemId` 不適用）
   - 例：倉管做庫存 rebalance（把 Z01 滯銷品調到 Z02 補貨）
   - 例：盤點後倉位優化調撥
   - 例：未來採購可能主動跟同行屯貨（B5 範圍）

**schema 必須兼容兩種**，不能假設「所有 ST/TI/CO 都源自 SO」。

具體影響：
- `nx03_st_item.sourceSoItemId` 必須允許 null（手動調撥場景）
- `nx02_ti_item.sourceSoItemId` 暫時維持 NOT NULL（既有無手動建 TI 的 caller）
- `nx04_co.sourceSoItemId` 必填（CO 必由 SO 觸發）
- 填寫責任在 caller：translator 必填、手動類 service 不填

這段是 v1 漏的場景，2026-04-25 D4 實作時被 transfer.service 既有 code 揭露。

### 2.2 物理庫存 vs 業務承諾的雙帳

兩個視角：
- **倉管看「物理庫存」**：實際盒子數，永遠 >= 0
- **業務看「可承諾數」**：物理 + 已承諾未出（後者可為負）

業界既有做法（偉盟）的痛點：負庫存出現後沒人知道是誰造成的。NEXORA 必須解決：

任何時候業務或倉管都能反查：「這個料號在這個倉的可承諾數是 -18，是哪些 SO 造成的？」→ 系統要能列出 SO 清單與對應業務、客戶。

### 2.3 一張 SO 對多張包貨單與送貨單

業界事實：包裝會因體積拆批。一張 SO 5 個料號可能拆成 2 張包貨單（大件分別包），可能拆成 3 趟送貨。

新邏輯：
- SO 對撿貨單 = 1:1（撿貨是一次動作）
- SO 對包貨單 = 1:N（依包裝體積拆）
- SO 對送貨單 = 1:N（依配送拆批）

每張包貨單要記錄「**裝了 SO 的哪幾個明細**」，這樣倉管才能知道哪幾項到了哪幾項還沒。

### 2.4 明細的兩段獨立進度

每個明細在系統內走兩段：

**第一段：補貨進度**（這項貨備齊了沒？）
- 等待補貨單建立 → 補貨中 → 補貨完成

**第二段：出貨進度**（這項貨出去了沒？）
- 等貨 → 撿貨中 → 包貨中 → 配送中 → 已送達

兩段串接：補貨完成後才能進入撿貨。

整張 SO 的狀態由所有明細的進度匯總而來，不再由 header 直接持有單一狀態。

### 2.5 補貨單與銷貨明細的雙向追蹤

每張自動建的補貨單（調撥/詢價/CO），必須記錄「我是為了哪張 SO 的哪個明細而存在」。
每個銷貨明細也要記錄「我等的是哪張補貨單」。

這個雙向關聯是「committed_stock 反查」的基礎，也是倉管/採購工作台「我為什麼要做這件事」的解釋來源。

## 3. 需求規格

下面 5 條是必須達成的功能，達成方式由 Hank 對照真實 schema 決定。

### 3.1 銷貨明細必須能標來源

每個銷貨明細必須有「補貨來源類型」+「補貨來源指向」兩個概念。

- 來源類型有 4 種固定值（self / transfer / inquiry / co），新增倉庫或同行**不應該需要動 schema**
- 來源指向是動態值（指到某個倉庫、某個同行、某個 CO 單）

具體欄位拆法（單欄 polymorphic / 雙欄 type+ref / 多欄各自 FK）由 Hank 取捨。

### 3.2 庫存必須有雙帳

物理庫存與會計庫存要能分離：
- 物理由倉管動，永遠 >= 0
- 會計由系統自動算（業務新增 SO 自動扣、出貨完成自動結），可為負

雙帳的實作方式（同表加欄位 / 拆獨立表 / 走 view）由 Hank 取捨。

關鍵約束：應用層程式碼**不應該直接寫會計庫存**——它必須由系統自動維護（trigger 或同等機制），避免業務邏輯 bug 導致雙帳錯亂。

### 3.3 反查能力

任何時候系統都要能回答：「料號 X 在倉 Y 的會計庫存為負，是哪些銷貨明細造成的？」

回傳要含：相關的 SO 編號、客戶、業務、明細數量、目前進度（補貨中還是等貨中）。

### 3.4 包貨單與送貨單支援 1:N

一張 SO 可以對應多張包貨單，每張包貨單要記錄「裝了 SO 的哪些明細」。
送貨單同理。

關聯實作（陣列欄位 / 中介表）由 Hank 取捨。

### 3.5 明細狀態雙段

每個銷貨明細需要兩段進度欄位：補貨段 + 出貨段。

整張 SO 狀態由所有明細的進度匯總，**不再由 SO header 直接持有單一狀態 enum**。

匯總邏輯：
- 全部明細「已送達」→ SO 完成
- 任何明細「撿貨/包貨/配送中」→ SO 出貨中
- 任何明細「等貨」→ SO 備貨中
- 都不是上面 → SO 仍是建立中（理論上不會發生，建單後會立刻離開）

匯總邏輯實作位置由 Hank 決定（DB view / application service / trigger 都可）。

## 4. Breaking change 業務效果

### 4.1 既有資料的處置原則

- 既有 SO 與其明細：補預設值（all self、補貨完成、已送達），等同於「歷史單，已結案」
- DEMO 用的特殊情境 mock 資料：手工補正確值，保留情境效果
- 既有包貨單/送貨單的 1:1 結構：保留可讀，但 deprecated（新邏輯不走這條）

### 4.2 既有畫面的處置

7 個既有畫面（庫存中心 5 個 workstation + 銷售中心首頁 + sop-demo Step8）需要改讀新後端。
- 庫存中心 5 頁 + 銷售中心首頁 → Phase 2b 改讀新後端
- sop-demo Step8 → 維持讀舊邏輯（屬教學模式）

### 4.3 deprecated 欄位策略

舊欄位（單值的包貨/送貨編號）標 deprecated 但保留一段時間，等教學模式邏輯穩定後再正式移除。具體保留多久由 Hank 工程判斷。

## 6. 開放問題（給 Hank 工程判斷）

這些問題 Alex 沒有立場判斷，由 Hank 對照真實 schema 與工程經驗決定。決定後在實作 spec 內記錄理由即可，不需回 Crown 拍板（除非影響業務行為）。

4. **deprecated 欄位保留多久**：建議用 trigger 防寫入而非實際刪欄位（Hank 已建議，採用）
5. **明細狀態匯總邏輯放哪一層**：DB view / application service / trigger 三選一
6. **race condition 處理**：advisory lock vs SELECT FOR UPDATE，hash key 怎麼算（Hank 已在 D3 v1 review 給 hashtextextended 建議，採用）
