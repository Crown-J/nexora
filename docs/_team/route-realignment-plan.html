一、業界基準（別人怎麼做）

「系統內部用代碼、對外用人看得懂的名字」是成熟系統的通用分層做法，不是我們發明的。常見三層：

層給誰看命名原則NEXORA 對應
內部模組 / 程式碼工程師、維運穩定代碼，永不隨業務改名而變features/nx0X、後端 nx0X
對外路由 / 網址客戶業務語意、好懂、好記、可分享/dashboard/{業務名}
顯示文字 / 選單客戶業務中文名進貨 / 庫存 / 銷貨…

關鍵慣例：對外名字可以變、對內代碼不該變。所以網址改成業務名，但資料夾保留 nx0X 編號——這正是執行長定的方向。

二、痛點分析（現在為什麼亂）

痛點 1：前端編號停在舊制、與後端錯位

早期編號是 nx00=主檔、nx01=採購…；後來整批 +1 改成 nx01=主檔、nx02=採購…。後端已改新制，前端 features 還停在舊制，於是同一個編號前後端意思差一位：

編號後端（新制）前端 features（舊制殘留）狀態
nx01主檔採購（po/rfq/rr）錯位
nx02採購庫存錯位
nx03庫存銷貨 workflow + 庫存混雜錯位+混雜
nx05/nx08財務 / 報表財務 / 報表已對齊

痛點 2：客戶端網址露 NX 代碼（違產品鐵則）

共 102 條活躍頁面露出 /dashboard/nx0X，全 repo 被硬寫引用 372 次。客戶會直接看到內部代碼，違反「對外不露代碼」鐵則。

痛點 3：擺錯資料夾 + 死碼殘留

採購 feature 內混了散主檔；nx03 同時裝銷貨與庫存；另有 4 個被取代但沒刪的死 hub。這些讓「一個資料夾 = 一個業務」的直覺破功。

三、設計｜A. 前端 features 編號校準對照

把前端 features 編號往後挪、對齊後端新制，同時把擺錯的東西歸位。

現況前端→校準後內容怎麼動
features/nx01（採購+散主檔）→features/nx02採購相關留下改 nx02；散主檔（customer-grade/engine/model/phonetic-dictionary/vehicle-classification）搬回主檔區（base）
features/nx02（庫存）→features/nx03整體對齊後端庫存=nx03；與既有 features/inventory 整併
features/nx03（銷貨+庫存混）→拆解銷貨 workflow 併入 features/sale（後端 nx04）；stock-balance 併入庫存（nx03）；原 nx03 資料夾清空刪除
features/nx05（財務）→features/nx05已對齊，不動
features/nx08（報表）→features/nx08已對齊，不動
⚠️ 撞名風險與對策：編號往後挪會出現「新舊 nx02 並存」的瞬間。施工必須由後往前、且每步先確認目標編號沒被占用，避免覆蓋。詳見第五節施工順序。

四、施工總原則

  • 每段獨立 commit，訊息寫清楚動了什麼。
  • 每段做完先驗證：tsc --noEmit 0 錯誤 + grep 確認舊路徑/舊引用歸零 + 能起 dev。
  • 舊網址留 redirect：每條舊 /dashboard/nx0X 改名後，保留一條 redirect 指向新業務名網址（防書籤/外部連結失效），過渡期後再評估移除。
  • 由低風險到高風險：先清死碼、再改引用最少的模組、最後才動最大的採購/報表。
  • 任一段驗證沒過就停手回報 CTO，不硬推。

五、分階段施工順序

段 0｜清死碼（暖身、零風險）

刪 4 個確定死檔；查清並處置 3 個待確認檔。先把雜訊清掉，後面校準看得更清楚。

驗證：tsc 0 錯誤、grep 死碼類名歸零。

段 1｜改「引用最少、無編號錯位」的模組網址（練手）

順序：nx07 人資（20）→ nx09 知識管理（23）→ nx06 配送（36）。這三個後端編號已對、前端也無 feature 撞名，純改網址 + 加 redirect，風險最低。

驗證：每改一個，tsc + grep /dashboard/nx0X 歸零 + 新網址可進。

段 2｜改已對齊模組的網址：財務、報表

nx05 → finance（29）、nx08 → report（60）。後端編號已對、前端 feature 編號也已對，只差網址沒改，先收這兩個。

驗證：同上。報表 60 處引用較多，改完仔細 grep。

段 3｜前端 feature 編號校準（核心、由後往前避撞名）

處理錯位段。順序由後往前：先把 features/nx03（銷貨+庫存混）拆解清空 → 再 features/nx02（庫存）改 nx03 → 最後 features/nx01（採購）改 nx02 並把散主檔搬回 base。每步先確認目標編號已空，再搬，避免覆蓋。

驗證：每搬一個 feature，全域更新 @/features/nx0X import 路徑、tsc 0 錯誤、grep 舊路徑歸零。

段 4｜改最大的網址：採購、銷貨、庫存（含拆分）

nx02 → purchase（95，庫存子頁分流到 inventory）、nx04 → sale（43）、nx03 → inventory+sale 拆分（37）、nx01 root 併入 purchase 並清掉「露碼跳露碼」的雙重 redirect。這是工程量最大、最後做。

驗證：tsc 0 錯誤、所有 /dashboard/nx0X 引用歸零（nx10 除外）、各業務網址可進、dev 兩端起得來。

段 5｜收尾

更新 menu/nav/dock config、面包屑；複查全 repo 再無 /dashboard/nx0X（nx10 除外）；更新線路圖文件與 README。

六、回滾點

  • 每段一個 commit，出錯可單段 revert，不影響其他段。
  • 段 3（編號校準）風險最高，施工前先在分支打 tag，萬一搬到一半亂掉可整段退回 tag。
  • 全程在重整分支進行，main 不受影響；全部驗證通過、CEO 確認後才合 main。
