# 銷售出貨履約流程重設計：撿貨 → 包貨 → 出貨

**版本** v0.1 意圖捕捉 ｜ **來源** 2026-07-22 執行長口述 ｜ **維護** Hank ｜ **狀態** 待新對話 grep 現況 + 執行長確認開放項

---

## 0. 這份在幹嘛

銷售流程要走完、卡在撿貨。目前撿貨被做成「**新增撿貨單**」，跟原設計不同。這份把執行長要的正確流程捕捉下來，當新對話的起手規格。定位：這是一條**劇本**（銷售出貨履約），穿過 銷售(SO) → 庫存共用能力(撿/包/出庫) → 配送(nx06)，符合三層架構模型（見 [[NEXORA-模組重定義分析]]）。

## 1. 執行長要的正確流程

### 1-1. 撿貨清單（不是「新增撿貨單」）
- **是一個清單／工作池**，不是一張要「新增」的單。
- **所有要出貨的東西都丟進這裡。**
- 倉管**用手機**依照這份清單作業。
- 撿完之後**回報**，東西再傳到包貨單。

### 1-2. 包貨單（這裡才是「新增」）
- 撿好回報的貨進來後，**新增包貨單**。
- 新增時**產生包裹編號**，列印出來貼在包裹上。
- 把撿好貨的東西**拉進來**（撿貨回報 → 包貨單）。
- 包完之後**封箱**。

### 1-3. 封箱後依「出貨方式」路由三區
| 出貨方式 | 去哪 | 倉管動作 |
|---|---|---|
| **自取** | 自取區 | 客人來自取時做**簽收** |
| **寄貨** | 寄貨區 | 倉管輸入**物流公司 + 物流編號**、拉進包裹單 |
| **配送** | 配送區 | 倉管**配單給外務**、拉銷貨單號連動、看有哪幾個包裹 |

## 2. 現況盤點（2026-07-22 grep）

**零件多半已存在，缺的是「工作池式入口 + 流程串接 + 三區路由」：**

- 後端：`nx03/pk`（撿貨）、`nx03/pl`（包貨）、`nx03/parcel`（包裹）、`nx06/pickup`（自取）、`nx06` Dn（配送）。
- 前端：`apps/nx-ui/src/app/dashboard/inventory/picking`＋`packing`；`features/nx03/picking`＋`packing`；手機版工作站早有（撿貨/包貨/配送，見歷史 closure）。
- 狀態機：`fulfillStatus W→PK→PL→D` 已存在（`nx03/pk/pk.service`、`nx03/pl/pl.service`、`nx04/so/so.service`、translator）。
- 資料表：`nx03_pk/pk_item`、`nx03_pl/pl_item`、`nx03_parcel`、`nx06_dn/dn_item/dn_stop`。

**核心落差**：撿貨目前是「新增撿貨單」的單據式操作；要改成「**要出貨的自動進撿貨池 → 手機撿 → 回報 → 餵包貨單**」的工作池式。

## 3. ⚠️ 待執行長確認的開放項（新對話動手前先問）

1. **撿貨池的粒度**：以「銷貨單行」進池還是整張 SO？多張 SO 能不能合併撿？
2. **撿貨清單 vs 現有 `nx03_pk` 表**：新「清單」是沿用 pk 表當底層、只把入口從「新增單」改成「池／看板」？還是 pk 表要重新定位？撿完回報寫哪張表？
3. **包貨拉貨的跨度**：一張包貨單能否跨多張 SO？一張 SO 能否拆多箱（多包裹）？**包裹編號規則**？
4. **出貨方式來源**：路由三區依據的「出貨方式」欄位在 SO 上嗎？（grep 確認）
5. **三區是什麼**：實體區還是系統看板／佇列狀態？（研判＝看板視角，各區一個工作佇列）
6. **配送區接 nx06 Dn**：配送配單給外務、拉 SO 看包裹——是不是直接接現有 `nx06_dn`？自取接 `nx06/pickup`？寄貨的物流欄位寫哪？

## 4. 建議做法（新對話參考、非定案）

## 5. 拍板收斂（2026-07-22 grep 現況後、執行長逐項拍板 → 本節為實作依據，v0.1 §3 開放項就此定案）

### 5-A. grep 實測補充（動手前的真相）
- **銷貨單自己走 DRAFT→CONFIRMED→PICKING→SHIPPED→INVOICED/COMPLETED**，扣庫存＋開應收＋產配送單目前**全綁在 PICKING→SHIPPED 那一刀**（`so.service` applySoShipping / createArFromShippedSo / createDeliveryDnFromShippedSo）。
- 撿貨/包貨/包裹（`nx03_pk`/`nx03_pl`/`nx03_parcel`）是**平行作業層**，只推進銷貨行 `fulfillStatus`（W→PK→PL→D→F），**不扣帳**。
- **無任何「SO→自動進撿貨池」程式**；`refreshment-doc-creator` 只對缺貨行（T/G/B）建補貨單，現貨行(S)不建撿貨單。撿貨現況＝手動「+新增撿貨單」。
- 手機工作站**沒有撿貨、包貨頁**（只有收貨/盤點/調撥取貨/同行取貨）。
- 出貨方式 `deliveryType`（D配送/P自取/C寄貨）**已在銷貨單表頭**；配送 `nx06_dn`（`DnItem.parcelId` 可掛包裹）、自取 `nx06/pickup`、寄貨欄位（`nx03_pl.logisticsProvider/logisticsTrackingNo`）都已存在。
- 銷貨行雙段狀態：`transferStatus`（P待補/I補貨中/C補貨完成）＋ `fulfillStatus`（W等貨/PK撿貨中/PL包貨中/D配送中/F已送達）。

### 5-B. 六項拍板
| # | 議題 | 拍板 |
|---|---|---|
| **D1** | 撿貨形態 | **撿貨表頭拆掉、變一張純清單（工作池）**。倉管眼前看不到「撿貨單」。池 = 現貨已備齊、還沒撿的**銷貨行**；每行狀態只有 **撿貨中 / 已撿完** 兩種。`nx03_pk` 表**留作隱形底層帳**（系統自動開、倉管無感），當接往包貨的橋。 |
| **D2** | 包貨跨度 | **一張包貨單可跨多張 SO**（同車同客戶併包）。→ 需放寬現行「包貨單只綁一張撿貨單」的 schema 綁定（見 5-D）。一張 SO 可拆多箱（多包裹）。 |
| **D3** | 裝置分工 | **撿貨＝手機/平板**（人在倉庫走動、不可能帶電腦）；**包貨、配送＝可能用電腦**。 |
| **D4** | 過帳時點 | **扣庫存＋開應收移到「交貨簽收後」**，封箱不落帳（封箱後還可能改單）。 |
| **D5** | 寄貨過帳點 | 寄貨無客戶簽收回報 → **交給物流、輸完物流單號那一刻就過帳**（視同已出貨）。 |
| **D6** | 出庫狀態語意 | 過帳移走後，**`SHIPPED` 重定義＝「已出倉、待簽收」**（封箱/出倉時到此）；**簽收（自取簽收／配送送達簽收／寄貨輸單號）才真正落帳** → SO 進 `COMPLETED`（狀態機 SHIPPED→COMPLETED 已存在）。 |

### 5-C. 目標流程（收斂後全鏈）
```
銷貨單確認(CONFIRMED)
  └─ 現貨行(transferStatus=C) 自動進【撿貨池】(fulfillStatus=W 待撿)
        ▼ 撿貨（手機/平板）
【撿貨池】清單：待撿 → 撿貨中 → 已撿完   ← 無表頭，倉管只操作銷貨行；底層自動維護 nx03_pk
        ▼ 包貨（平板/桌機）
【包貨單】撈「已撿完」的行（可跨 SO）→ 產包裹號 BX-年月-倉-流水 → 列印貼箱 → 封箱
        ▼ 封箱 → SO=SHIPPED(已出倉待簽收) + 依 deliveryType 路由三區；配送於此時產 nx06_dn 草稿
┌─────────────┬──────────────────┬────────────────────────────┐
│ 自取區(P)   │ 寄貨區(C)        │ 配送區(D)                  │
│ 櫃台桌機    │ 包裝桌機         │ 組長桌機配單 + 外務手機跑  │
│ 客人取貨    │ 輸物流商+單號    │ 配單給外務→外務跑→客簽收   │
│ →簽收       │ →標記寄出        │ →送達簽收                  │
│ →【過帳】   │ →【過帳】(D5)    │ →【過帳】                  │
└─────────────┴──────────────────┴────────────────────────────┘
        ▼ 過帳 = applySoShipping(扣庫存) + createArFromShippedSo(開應收) + SO→COMPLETED + fulfillStatus F
```

### 5-D. 需要的 schema 調整（⚠️ 執行長 review 後才實作）
- **放寬包貨單綁定**：現 `Nx03Pl.pkId` 必填（一包貨單綁一撿貨單）＋ `Nx03PlItem.pkItemId` 必填。要支援「跨 SO 撈已撿完行併一張包貨單」，需把 PL→PK 的硬綁改成鬆綁（`pkId` 改選填或改由 plItem 逐行溯源）。**細節設計待 5-E 階段 2 前另出 schema 提案給你 review**。
- 其餘（撿貨池、三區佇列）**用既有欄位即可、不必動 schema**。

### 5-E. 分階段路線圖（漸進式、逐段 commit；破壞性的排後面、動前先 review）
- **階段 1 撿貨池（不破壞、可先做）**：SO 確認→現貨行自動進池；撿貨池清單 API（讀銷貨行、非撿貨單）＋手機/平板撿貨頁（待撿→撿貨中→已撿完）；底層自動維護 nx03_pk。舊「+新增撿貨單」桌機頁降級/隱藏。
- **階段 2 包貨（含 schema 微調、動前 review）**：包貨單撈「已撿完」行（可跨 SO）＋產包裹號＋列印貼紙＋封箱；schema 放寬 PL 綁定。
- **階段 3 三區路由 ＋ 過帳搬移（破壞性、動前 review）**：封箱後路由三區佇列；把 applySoShipping/開應收從 PICKING→SHIPPED 拆出、改掛到「簽收／寄貨輸單號」；配送單產生時點提前到封箱；SHIPPED 語意改「已出倉待簽收」、簽收進 COMPLETED。
- **階段 4 收尾**：操作手冊、迴歸腳本、舊太空風 picking/packing 頁清理。

⚠️ 階段 2 的 schema 提案、階段 3 的過帳搬移，都屬「Schema 設計決定／破壞性業務邏輯」→ 依 CLAUDE.md §12 先給執行長 review 才實作。階段 1 為非破壞、可先動手。
