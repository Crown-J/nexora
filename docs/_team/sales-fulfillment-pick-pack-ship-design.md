# 銷售出貨履約流程重設計：撿貨 → 包貨 → 出貨

**版本** v0.1 意圖捕捉 ｜ **來源** 2026-07-22 執行長口述 ｜ **維護** Hank ｜ **狀態** 待新對話 grep 現況 + 執行長確認開放項

---

## 0. 這份在幹嘛

銷售流程要走完、卡在撿貨。目前撿貨被做成「**新增撿貨單**」，跟原設計不同。這份把執行長要的正確流程捕捉下來，當新對話的起手規格。定位：這是一條**劇本**（銷售出貨履約），穿過 銷售(SO) → 庫存共用能力(撿/包/出庫) → 配送(nx06)，符合三層架構模型（見 [[NEXORA-模組重定義分析]]）。

## 1. 執行長要的正確流程

### 1-1. 撿貨清單（不是「新增撿貨單」）
- **是一個清單／工作池**，不是一張要「新增」的單。
- **所有要出貨的東西都丟進這裡。**
- 倉管**用手機**依照這份清單作業。
- 撿完之後**回報**，東西再傳到包貨單。

### 1-2. 包貨單（這裡才是「新增」）
- 撿好回報的貨進來後，**新增包貨單**。
- 新增時**產生包裹編號**，列印出來貼在包裹上。
- 把撿好貨的東西**拉進來**（撿貨回報 → 包貨單）。
- 包完之後**封箱**。

### 1-3. 封箱後依「出貨方式」路由三區
| 出貨方式 | 去哪 | 倉管動作 |
|---|---|---|
| **自取** | 自取區 | 客人來自取時做**簽收** |
| **寄貨** | 寄貨區 | 倉管輸入**物流公司 + 物流編號**、拉進包裹單 |
| **配送** | 配送區 | 倉管**配單給外務**、拉銷貨單號連動、看有哪幾個包裹 |

## 2. 現況盤點（2026-07-22 grep）

**零件多半已存在，缺的是「工作池式入口 + 流程串接 + 三區路由」：**

- 後端：`nx03/pk`（撿貨）、`nx03/pl`（包貨）、`nx03/parcel`（包裹）、`nx06/pickup`（自取）、`nx06` Dn（配送）。
- 前端：`apps/nx-ui/src/app/dashboard/inventory/picking`＋`packing`；`features/nx03/picking`＋`packing`；手機版工作站早有（撿貨/包貨/配送，見歷史 closure）。
- 狀態機：`fulfillStatus W→PK→PL→D` 已存在（`nx03/pk/pk.service`、`nx03/pl/pl.service`、`nx04/so/so.service`、translator）。
- 資料表：`nx03_pk/pk_item`、`nx03_pl/pl_item`、`nx03_parcel`、`nx06_dn/dn_item/dn_stop`。

**核心落差**：撿貨目前是「新增撿貨單」的單據式操作；要改成「**要出貨的自動進撿貨池 → 手機撿 → 回報 → 餵包貨單**」的工作池式。

## 3. ⚠️ 待執行長確認的開放項（新對話動手前先問）

1. **撿貨池的粒度**：以「銷貨單行」進池還是整張 SO？多張 SO 能不能合併撿？
2. **撿貨清單 vs 現有 `nx03_pk` 表**：新「清單」是沿用 pk 表當底層、只把入口從「新增單」改成「池／看板」？還是 pk 表要重新定位？撿完回報寫哪張表？
3. **包貨拉貨的跨度**：一張包貨單能否跨多張 SO？一張 SO 能否拆多箱（多包裹）？**包裹編號規則**？
4. **出貨方式來源**：路由三區依據的「出貨方式」欄位在 SO 上嗎？（grep 確認）
5. **三區是什麼**：實體區還是系統看板／佇列狀態？（研判＝看板視角，各區一個工作佇列）
6. **配送區接 nx06 Dn**：配送配單給外務、拉 SO 看包裹——是不是直接接現有 `nx06_dn`？自取接 `nx06/pickup`？寄貨的物流欄位寫哪？

## 4. 建議做法（新對話參考、非定案）

1. 先 grep 完整現況：pk/pl/parcel/pickup/dn 的表結構、service、現有 UI 動線、fulfillStatus 全流轉。
2. 對照本檔 §1 目標流程，列「現況 vs 目標」落差表。
3. §3 開放項問執行長拍板。
4. 漸進式：撿貨池入口 → 撿貨回報→包貨串接 → 包裹編號/封箱 → 三區路由，逐段 commit。
5. 手機優先（倉管用手機）。
