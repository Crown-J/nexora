# 庫位級庫存（Bin-Level Stock）規格提案 v0.1

> 提案人：Hank｜日期：2026-07-23｜狀態：**待執行長 review**（此文件只提案、尚未動 code）

---

## 1. 為什麼做（問題陳述）

恆迎的壞習慣：庫存**只設到「倉位（倉庫）」、沒認真規劃「庫位」**，導致貨常找不到、盤點對不上、新人上手慢。NEXORA 要避開這個負面教材——**知道每一格庫位實際有幾個什麼貨**。

---

## 2. 現況盤點（grep 實查、非憑印象）

| 項目 | 現況 | 缺口 |
|---|---|---|
| **庫位主檔層級** | ✅ 已建**五層**：據點 `nx01_site` → 倉庫 `nx01_warehouse` → 區域 `nx01_warehouse_zone` → 貨架 `nx01_warehouse_rack` → 庫位 `nx01_location`（2026-06-22~28 完成） | 層級不缺 |
| **庫存餘額** | `nx03_stock_balance` 鍵＝（租戶＋料件＋**倉庫**）；欄位 onHand/reserved/available/inTransit/avgCost | ⛔ **無庫位維度**、不知道哪格幾個 |
| **庫存流水** | `nx03_stock_ledger` **已有 `location_id`（NOT NULL）**、每筆進出都記在哪格發生 | 地基半成、但無「按庫位加總的餘額」可快查 |
| **料件庫位** | `nx03_part_stock_setting.default_location_id`＝一料一個「建議擺放庫位」單值 | 只是建議、非實際多庫位分佈 |
| **進出邏輯** | `applyQtyInWithLedger` / `applyQtyOutWithLedger` 更新倉庫餘額 + 寫流水（帶 locationId、實務多塞預設庫位） | 只維護倉庫餘額、不維護庫位餘額 |
| **賣貨/成本** | 可用量、保留量、avgCost 全在**倉庫級** | 跟庫位無關（見 §4） |

**一句話**：層級架構齊、流水已記庫位、**只差「庫位級餘額」這張表 + 進出時同步維護它**。

---

## 3. 目標與設計原則

1. **加一層 physical、不動賣貨引擎**：庫位餘額＝實體分佈；賣貨可用量/保留量/成本仍走倉庫級。降風險。
2. **倉庫餘額仍是主帳**：`sum(某料在某倉各庫位的 onHand)` ＝ 該倉 onHand（交易內恆等式，強制對帳）。
3. **漸進、非破壞**：既有倉庫餘額不動；庫位餘額 additive 疊上去；先遷移、後逐步 bin-aware。
4. **撿貨三欄長在上面**：撿/包/放回自然變「庫位間搬移」。

---

## 4. 對賣貨 / 成本 / 可用量的影響 ＝ 幾乎沒有 ⭐

- **可用量/保留量**（賣得出去幾個）＝邏輯庫存、跟貨放哪格無關 → **維持倉庫級**、不動。
- **avgCost（移動平均）**＝業界慣例算到倉庫級、不逐格算 → **維持倉庫級**、不動。
- **庫位餘額只記 onHand（實體幾個在哪格）**、給「找貨/撿貨/盤點/上架」用。
- ⇒ 銷貨、應收、成本、保留全部**不受影響**，改動面集中在「進出時多維護一張庫位餘額表 + 顯示」。

## 5. Schema 設計（提案、待拍板）

### 5.1 新增：庫位級餘額 `nx03_stock_location_balance`

```
model Nx03StockLocationBalance {
  id           String   @id
  tenantId     String
  partId       String
  warehouseId  String
  locationId   String        // 到庫位（bin）
  onHandQty    Decimal  @default(0)   // 這一格實際幾個
  lastMoveAt   DateTime @default(now())
  isActive     Boolean  @default(true)
  ...createdBy/updatedBy...
  @@unique([tenantId, partId, warehouseId, locationId])
  @@index([tenantId, warehouseId, locationId])   // 「這格有什麼」查詢
  @@index([tenantId, partId])                     // 「這料在哪些格」查詢
}
```
- **只放 onHandQty**（實體）；reserved/available/avgCost 不放這裡（留倉庫級）。
- 倉庫餘額 `nx03_stock_balance` **不動**，繼續當賣貨主帳。

### 5.2 系統庫位（暫存/流程用）

每倉預建幾個**系統庫位**（沿用 Z00 主區預建範式），`nx01_location` 加一個 `locationType`（或 `isSystem` 旗標）分類：

| 系統庫位 | 用途 |
|---|---|
| 收貨暫存 | 進貨到貨、還沒上架 |
| 待包暫存 | 撿貨撿起來、還沒包貨（撿貨頁「中欄」） |
| 待上架 | 訂單取消/退回、貨要放回架上（撿貨頁「右欄」） |
| （未指定） | 遷移過渡：舊資料沒設庫位的貨先進這格 |

⚠️ 待拍板：**要不要「A員工庫位」**（每個撿貨員一格、表示貨在誰身上）。
**我建議不要**——待包暫存一格就好，「貨在誰身上」用撿貨明細的撿貨人記錄即可；除非要逐人結算手上實物。

## 6. 進出如何變「庫位感知」

- 流水 `location_id` 已有、**不動**。
- `applyQtyIn/Out`：除了更新倉庫餘額，**同步 upsert 庫位餘額**（該 location ±qty）。這是核心改動點、集中在 `nx03-inventory.ts` 兩支函式。
- 每筆進出**必須指定真庫位**：過渡期沿用料件預設庫位；之後 UI 逐步要求選格（上架/撿貨明確指定）。

**撿貨三欄 ＝ 庫位間搬移**：

| 撿貨頁欄位 | ＝哪個庫位 | 動作 |
|---|---|---|
| 左 待撿貨 | 料件的**儲位（原庫位）** | 撿 → 搬到待包暫存 |
| 中 已撿貨 | **待包暫存** | 取消撿貨 → 搬回原儲位（誤按修正）；包貨拉走 → 出 |
| 右 已取消 | **待上架** | 已放回 → 搬回原儲位 |

---

## 7. 遷移方式（非破壞）

1. 每倉預建系統庫位（收貨暫存/待包暫存/待上架/未指定）。
2. 回填 `nx03_stock_location_balance`：把每料在每倉的 onHand，**灌進它的預設庫位**（`default_location_id`；沒設的進「未指定」格）。→ 各格加總＝倉庫 onHand ✅ 恆等式成立。
3. 倉庫餘額不動、賣貨零影響。可重跑的回填腳本 + 對帳查核（每倉每料：Σ庫位 = 倉庫）。

## 8. 分階段路線圖（提案）

| 階段 | 內容 | 產出 |
|---|---|---|
| **P0 地基** | 新表 + 系統庫位 + 回填 + 對帳；`locationType` 加旗標 | 有庫位餘額、行為不變 |
| **P1 同步維護** | `applyQtyIn/Out` 同步 upsert 庫位餘額 + 「這格有什麼/這料在哪」查詢與顯示 | 庫位餘額即時準 |
| **P2 撿貨三欄** | 上架指定格、撿貨＝庫位搬移；撿貨頁改左中右三欄（電腦）/三頁（手機） | 您要的撿貨改版落地 |
| **P3 進階** | 庫位盤點、庫位間調撥、按庫位補貨、找貨搜尋、上架建議 | 完整 WMS 能力 |

> 撿貨三欄改版（您這次的需求）需要 P0+P1+P2；P3 之後再排。

## 10. 我的整體建議

- 走 **P0→P1→P2**：先把庫位餘額地基鋪好（風險低、賣貨零影響），撿貨三欄自然長上去、不會做一版打掉。
- **員工庫位不設**、成本/可用量**維持倉庫級**——把改動面壓到最小、只加「實體在哪格」這一層。
- 版本歸屬傾向 **LITE 核心**（找得到貨是基本盤、不該當加購擋住），但這條請您定。
